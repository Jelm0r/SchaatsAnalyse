# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A skater-analysis tool with **two interchangeable detection backends** and a shared core:
- `skate_analysis.py` — the CLI + the shared core (angle calculation, weight detection, push segmentation, offline smoothing, drawing) **plus** the MediaPipe backend. Detects the push leg, calculates the push angle relative to the ice and the knee angle, and can write an output video with overlay + HUD. Also recognizes when the skater **isn't facing the camera** (the corner) and keeps those frames out of the measurement.
- `skate_yolo.py` — the **YOLO-pose + ByteTrack backend** (ultralytics) with **offline target selection**: first collects *all* detections from *all* frames (at high resolution), then chooses the target skater globally via **suit color** (torso HSV histogram) + **direction of travel** (constant-velocity prediction), and refines the keypoints with a **top-down refinement pass** — **RTMPose-26** (rtmlib/ONNXRuntime, with real heel/toe keypoints) if rtmlib is present, otherwise the older YOLO-crop route. Produces the same `FrameResult` list as the MediaPipe backend, so the shared core works unchanged. Robust against crossing skaters, occlusion, and motion blur. **Skips most of the corner** (`_CornerGuard`): there's nothing to measure there and the detection pass is the lion's share of the analysis time. **Follows a too-small skater from a drawn box** (`_Spyglass`, opt-in via `doel_kader`): the detection pass only sees a skater from ~80–130 px onward, so the refinement pass then propagates the bbox itself from frame to frame. Needs a separate environment (torch), see below.
- `skate_gui.py` — PySide6 GUI: **home page = the library** (skaters on the left, their analyses on the right; a new analysis via a dialog, double-click = reopen in seconds). Plays the video back with the skeleton/push-leg overlay live on top (scrubbing, play/pause, layer toggles), a table of push angles (click a row → jump to that frame), an angle-over-time graph, CSV export. Also **two analyses side by side** ("Compare skaters", each independently controllable + "Start all" from a sync point) — made possible by the video panel as a reusable `VideoPlayer` widget. Analyses are automatically saved to the library afterward. Under **Recordings**, a raw recording can also simply be **viewed by hand** (`ViewWindow`: full screen, zoom/slow down, `.`/`,` scrub at 6×, saved points) — without an analysis, since not every clip needs to be measured. **Picks the backend automatically**: YOLO if torch/ultralytics is installed (`IS_YOLO`), otherwise MediaPipe — without loading those packages, see "Startup" below.
- `skate_db.py` — the **library** (ROADMAP phase 1): SQLite (`schaats.db`) + `media/<analysis-uuid>/` (video copy + `landmarks.npz`) + `opnames/` (raw, not-yet-trimmed training recordings, phase 8, with the points from the manual viewing window) in one configurable library folder. All SQL and path logic lives here; the GUI only talks to this module. Stdlib + numpy (via the phase 0 serialization in `skate_analysis.py`), importable in both venvs; self-test without video/GUI: `python skate_db.py`.
- `skate_environment.py` — **where the files live and where the output goes** (EXE.md step 1+2): `is_frozen()`/`app_dir()`/`data_dir()` + `start_log()` + **`start_crashlog()`**. Deliberately **stdlib-only** (no cv2/numpy/Qt), since it's the *only* module loaded before the GUI's splash screen; `skate_analysis.py` passes the three path helpers through, so `from skate_analysis import app_dir, data_dir, is_frozen` keeps working everywhere. **`start_log()` redirects as soon as there's no console** — frozen, or started with `pythonw.exe` (`sys.stderr is None`), or with the test hook `SKATEANALYSIS_LOG`. That `pythonw` branch isn't there for show: without the redirect, `sys.stderr` is `None` there, every `write` throws an `AttributeError`, and **all** application output disappears — prints, Qt messages, the screen-change log lines, the ultralytics lines. The log then still gets a session header, because `start_crashlog()` writes that separately whenever there's no redirect, and that reads as "the app is logging" while nothing actually lands in it. Cost a whole test session on 25 Aug 2026: `start_gui.bat` uses `python.exe` (console, so fine), but via a shortcut using `pythonw.exe` nothing from that run could be found afterward. **`start_crashlog()`** is the safety net underneath it (TODO_CRASH.md item 3): `faulthandler` writes the C stack of a fatal error to the same log file — via its **own file descriptor**, because faulthandler writes outside the normal Python machinery and can't do anything with the `_LogFile` wrapper (which has no `fileno()`) — and `sys.excepthook` + `threading.excepthook` catch unhandled Python errors, including from plain threads (backend warmup, local probe), where they used to vanish without a trace. Unlike the log, this **always** runs, even as a standalone script — that's exactly where debugging happens. Two things keep the file readable for whoever sends it in: every session ends via `atexit` with `=== cleanly shut down … ===` (that line is by definition missing after a hard crash), and the header explains why — needed because Qt systematically produces one handled COM exception on startup (`Windows fatal exception: code 0x8001010d` on the `app.exec()` line) that faulthandler reports anyway. **So a crash is: `access violation` or `Fatal Python error` with no closing line after it.** Self-test: `python skate_environment.py` — including a real access violation in a separate process (`faulthandler._read_null()`), since only that actually tests what it's there for.
- `skate_analysis.spec` + `build.bat` + `make_version.py` + `installer.iss` — **the bundled app and the installer** (EXE.md steps 3 and 4), placed alongside the modules above: not a single line of the modules above was changed for it, and the standalone scripts and both venvs run unchanged. `build.bat` generates `_version.py` with the git stamp (otherwise every analysis from the exe would land in the library without a version stamp), runs PyInstaller with the spec (onedir + windowed + noupx; onefile would unpack ~1.5 GB to `%TEMP%` on every start and undo exactly the startup work done above) and afterward places the three models **next to** the exe — deliberately not in the bundle, so a rebuild doesn't have to push them through the PyInstaller mill and `app_dir()` simply finds them. Two excludes carry the size (787 MB without models): PySide6 from 634 → 104 MB, and polars (177 MB, comes along via ultralytics but only used in training/plotting/export paths — confirmed by measurement with a `sys.meta_path` block that `model.track()`/`model.predict()` never load it). Building requires `pip install pyinstaller` in `.venv-yolo`. Afterward `build.bat` compiles **`installer.iss`** as step 4/4 with Inno Setup (6.3+, found in the per-user or machine folder or on PATH; not found = skipped with a message, the built folder stays usable) into `dist\SkateAnalysis-setup.exe` — **649 MB, ~5 min**, installs without admin rights to `{localappdata}\Programs\SkateAnalysis` (1,313 MB, 43 s) and on removal leaves `%LOCALAPPDATA%\SkateAnalysis` (the log) and the Drive library alone. Four `#if !FileExists` checks refuse to compile if the exe or one of the models is missing: an installer that looks fine but downloads 178 MB on the first analysis is worse than a build that fails outright. The version stamp travels along as `/DVersie=` (`make_version.py --show`, ASCII — the middle dot in `label` doesn't survive a `for /f` loop in cmd.exe) and shows up that way in "Apps & features"; `skateanalysis.ico` is the icon for the exe, the installer, and the shortcuts. **Close a running `dist\...\SkateAnalysis.exe` before a rebuild** — PyInstaller wipes the output folder and otherwise fails halfway with `PermissionError: [WinError 5]`. **The bundle has been measured against the source (EXE.md step 5):** an analysis from the exe matches the same analysis from the venv landmark-for-landmark (≤0.0001 px on x/y across all 33 points × 103 frames, the same pushes, legs, frame boundaries and angles, and ~90 s vs. 90.7 s) — no surprise, since all seven project modules in the bundle are byte-identical to the repo source and all 122 shared `.dll`/`.pyd` files are byte-identical to `.venv-yolo`. The DirectML route is simply on in the exe; the ultralytics line `Using ONNX Runtime … with CPUExecutionProvider` in the log is its own request from before the `_dml_sessions()` patch and says nothing about the provider actually used.
- `INSTALL.md` — **the instructions for the trainers** (EXE.md step 6), the only document in this folder not written for a developer. Contains what a colleague without Python and without admin rights needs: fetching the setup from `My Drive\SkateAnalysis\app\` (and making it available offline first — starting a 650 MB setup from the streaming drive can fail partway through), **the SmartScreen step** ("Windows protected your PC" → More info → Run anyway) with the reason alongside it, choosing the library folder on the shared Drive, setting the folder to *Available offline* (otherwise a single jump in the trim window costs 5–45 s), and where the log lives if something goes wrong — including the criterion from step 2: no `=== cleanly shut down … ===` after the last session means a crash. **The SmartScreen explanation is deliberately already in the introduction**: someone who unexpectedly sees that blue window doesn't click through, they call to ask if there's a virus. Deliberately **no certificate was bought** (€200–400/year for a handful of trainers). If the startup, library, or logging path changes, this document needs to change with it: it names paths (`%LOCALAPPDATA%\SkateAnalysis`), button names ("Your name...", "Library folder...", "Refresh") and numbers (~1 s/frame on the GPU, ~2× slower on the CPU) that are only correct as long as the app behaves that way.
- `skate_perspective.py` — **perspective correction via track lines** (ROADMAP phase 7): pure-numpy calibration (vanishing points → focal length → ice-plane↔world homography) and 3D angle reconstruction with two interchangeable knee constraints. Independently importable in both venvs (no cv2/scipy/torch); synthetic self-test: `python skate_perspective.py`. Opt-in, hooked into the pipeline via `PerspectiveConfig` (see architecture).
- `skate_eval.py` — **the measurement basis for tracking accuracy**: proxy metrics without ground truth (bone-length stability around the trend, jitter, coverage, L-R alternation), comparison of two analysis npz's, a report on the **corner signal** (`corner` subcommand: ratio trace + detected corner segments, to calibrate `CORNER_IN`/`CORNER_OUT` on new material), and a clicker to annotate a **golden reference** (knees/ankles in ~15 frames, two-stage click with magnification) → a real angle error in degrees. Every pipeline change should be checked against this (see also the phase 6 measurement protocol). **Always read the stance-leg number.** The golden angle error is split into stance leg and swing leg (on `r.leg`), and `compare` prints the A/B difference on the stance leg separately. Only the stance leg produces `PushEvent.angle`; the swing leg is hidden behind the stance leg head-on, where both the detector and the annotator are guessing. On one dataset the average was over six times too pessimistic (8.47° mixed vs. 1.34° stance leg on "Schaats frontaal.MOV") and dominated by those guesses, so a real gain of a few tenths of a degree got lost in it. **Note, since manually placed skeletons were introduced:** the coverage metric counts a hand-placed skeleton as detected, so an npz comparison from before/after a manual session no longer measures only the detector — compare detector changes on unedited analyses (`analysis.edited = 0`, or `landmarks_ruw.npz`). `RECORDING.md` contains the recording advice (4K, short shutter speed, 50/60 fps) — better recordings pay off more than algorithm work.

### Dependencies / environments

There are **two Python environments** because torch/ultralytics has no wheels for the standard Python 3.14, and Anaconda Python (3.12 here) clashes with PySide6's Qt DLLs:
- **MediaPipe backend**: Python 3.14 with `pip install mediapipe opencv-python numpy PySide6`.
- **YOLO backend**: `.venv-yolo` on **Python 3.11** (standalone, not Anaconda!) with `pip install ultralytics PySide6 lap onnxruntime tqdm` plus `pip install --no-deps rtmlib`. Created with `py -3.11 -m venv .venv-yolo`. The YOLO model weights (`yolo26x-pose.pt`, ~126 MB) sit next to the script; otherwise ultralytics downloads them on first use. The RTMPose-26 model (~178 MB ONNX) is downloaded by rtmlib on first use to `%USERPROFILE%\.cache\rtmlib`. **Note (1):** don't create the venv with Anaconda Python — then `import PySide6.QtCore` fails with "DLL load failed / The specified procedure could not be found". **Note (2):** always install rtmlib with `--no-deps` — it declares `opencv-contrib-python` as a dependency, and that would otherwise overwrite the existing cv2 install; rtmlib only really needs numpy+cv2+onnxruntime+tqdm.

**GPU (optional, but it's a factor of 2 to 10).** Both heavy passes run on the GPU as soon as one is present and otherwise just on the CPU — see `yolo_device()`/`yolo_dml()`/`rtmpose_device()` in `skate_yolo.py`. The setup differs **per pass and per GPU brand**, since the passes run on different engines and one says nothing about the other:
- **NVIDIA, detection pass (torch/ultralytics)** — `pip install ultralytics` pulls in the **CPU build** of torch by default (recognizable by `2.13.0+cpu` in `torch.__version__`), and that can never use CUDA in principle, however good the graphics card is. Replace it with the CUDA build that matches the driver: `pip install "torch==2.13.0+cu130" "torchvision==0.28.0+cu130" --index-url https://download.pytorch.org/whl/cu130`. `nvidia-smi` shows the highest CUDA version the driver supports in the top right; pick a `cuXXX` index at or below that number. Keep the torch version itself unchanged (2.13.0 here), so ultralytics can't trip over it.
- **NVIDIA, refinement pass (RTMPose/ONNXRuntime)** — `pip uninstall onnxruntime` + `pip install onnxruntime-gpu`. This is genuinely a separate step: ONNXRuntime doesn't get its CUDA support from torch, so with only the plain `onnxruntime` this pass stays on the CPU while the detection pass is already running on the GPU.
- **Integrated GPU (Intel/AMD): DirectML, for both passes at once** — `pip uninstall onnxruntime` + `pip install onnxruntime-directml` + `pip install onnx onnxslim`. Torch doesn't talk to an iGPU, so the detection pass here doesn't go through `device=` but through an **ONNX export of the same `.pt` model** that `_load_yolo` builds once (`yolo26x-pose-dml.onnx`, ~220 MB, in `.gitignore`) and which `_dml_sessions()` places on the DirectML provider — ultralytics itself only knows three providers (CUDA/CoreML/CPU) and has no switch for DirectML. OpenVINO was ruled out: that GPU plugin is Intel-only.

**Measured** on "Schaats frontaal.MOV" (103 frames, with a target click, `bocht=False`), against the same machine on the CPU:
- **RTX 3050 Laptop 4 GB (CUDA): 194.0 s → 19.5 s, 9.9x faster** (1.88 → 0.19 s/frame). Landmarks differ by subpixel amounts (median 0.048 px, p95 0.23 px); the only outliers up to ~3.6 px are on the **wrists** (lm 15/16) and the shoulder — points that feed no measurement at all.
- **AMD Radeon Graphics, integrated (DirectML): 220.6 s → 98.4 s, 2.2x faster** (2.14 → 0.96 s/frame), with **0.0 px** median difference on knees and ankles (p95 0.1 px); the RTMPose pass on DirectML is even bit-identical to that same pass on the CPU.

In both cases it's **the same measurement**: equal coverage (100/103), the same 8 pushes with the same legs, the same frame boundaries and the same angles. So GPU acceleration is pure time savings, not a silent change in the measurement, and old analyses stay comparable to new ones.

**Two pitfalls that measured differently ever so slightly** (both really went wrong while building the DirectML route, see GPU.md chapter 4):
- **The ONNX export must be `dynamic=True`.** Ultralytics letterboxes a `.pt` model rectangularly, but an ONNX model with a fixed input shape gets the image inside a square with a gray border — a different picture for the network. Measured with a static export: coverage 100/103 → **89/103** and two push angles **18° different**, while the raw per-frame detections were still nearly identical (the difference traveled through the gap-filling and the color gate in the refinement pass). With a dynamic input shape, the letterbox is identical again to that of the `.pt` model — and it costs no speed, since all frames of one video have the same shape.
- **`YOLO_AUTOINSTALL=false`** therefore sits at the top of `skate_yolo.py`, before the ultralytics import: the ONNX backend does `check_requirements("onnxruntime")` and installs that package unasked right over `onnxruntime-directml`, which silently makes the GPU route disappear.

`SKATEANALYSIS_CPU=1` forces both passes back to the CPU — needed to compare a GPU analysis against a CPU analysis without having to tear down the environment.

**`GPU.md`** has the full story: the setup per machine (which does **not** travel via git — `.venv-yolo/` is in `.gitignore`), the reference measurements for both routes, and the measurement protocol that proves an acceleration is *not* a change in measurement (including the bisect step: new model on the old provider, to separate export from arithmetic). Beyond that there's nowhere else to choose: without a GPU (or without the right wheels) every pass falls back silently **independently of the other**, a CUDA OOM partway through continues the rest of the run on the CPU instead of letting the analysis fail (`_infer`), and `_DmlYolo` does the same if DirectML drops out partway. **Watch which errors count as a device error.** `_infer` only falls back on the literal string `'out of memory'` and re-raises everything else; `_DmlYolo._call` initially did that on `except Exception` and thereby also logged a `numpy.linalg.LinAlgError: Singular matrix` from ByteTrack's **Kalman update** (`np.linalg.solve` in `ultralytics/trackers/utils/kalman_filter.py`) as if it were a GPU problem — with a message that pointed the user the wrong way *and* needlessly pushed the rest of the analysis onto the CPU (~2x slower). Such an arithmetic error happens *after* inference and says nothing about the device: `_call` now lets it through and `_detect_all` catches it, **restarts the tracker** (`_restart_tracker` → `BYTETracker.reset()` via `model.predictor.trackers`; the DML shell has a `__getattr__` passthrough for that) and redoes the frame on the same device. Deliberately no message to the user — nothing changes about the device or the measurement — but a log line does get written, since a pattern of frequent occurrence says something about the recording.

**Every tracker restart breaks the ByteTrack IDs, and that isn't free.** `BYTETracker.__init__` calls `reset_id()`, so both a restart and the CPU fallback make the IDs start over at 1 — while `_build_tracklets` groups purely by ID. Without a countermeasure, an old and a new track with the same number melt together into one tracklet, in the worst case two different skaters. `_detect_all` therefore keeps a **generation counter** (`model.generation` for the device switch + its own restarts) and has each generation start its IDs above the highest ID already handed out. Tested with a fake model that throws `Singular matrix` on frame 10 and hands out raw ID 1 in both generations: the frame is redone (20/20), the tracker restarts exactly once, and the result is two tracklets of 10 instead of one of 20. **On real material the payoff is time, not measurement.** The same clip with the error forced on frame 130, old vs. new handling: identical coverage (136/183) and the same 12 pushes — the ID collision there did merge 4 tracklets (28 vs. 32) but didn't change the outcome. What it did change: **211 s vs. 153 s**, because the fallback to the CPU used to be permanent. So don't expect this fix to recover measurements; it removes an incorrect message and an unnecessary slowdown.

`pose_landmarker_full.task` (the MediaPipe pose model, ~9.4 MB) must be in the same folder as the script. It's already there. If it's missing, download it again from:

https://storage.googleapis.com/mediapipe-models/pose_landmarker/pose_landmarker_full/float16/latest/pose_landmarker_full.task

## Important pitfall: MediaPipe API

This script uses the **new MediaPipe Tasks API** (`mediapipe.tasks.python.vision.PoseLandmarker`), not the old `mp.solutions.pose` API. The old "Solutions" API has been removed from recent mediapipe wheels (here: mediapipe 0.10.35 on Python 3.14) — `mp.solutions` simply no longer exists in this environment. So don't add code that relies on `mp.solutions.*`; use `PoseLandmarker.create_from_options(...)` with `running_mode=VIDEO` and `detect_for_video(mp_image, timestamp_ms)`, as in `analyze_video()`.

`cv2.putText` (Hershey fonts) doesn't support Unicode such as `°` — it renders as `??`. Use `"deg"` instead of the degree symbol in **on-screen text drawn with `cv2.putText`** (in `draw_hud`/`draw_leg_overlay`). This doesn't apply to Qt widgets in `skate_gui.py` (QLabel etc. render `°` just fine) — only to text drawn onto the frame pixels via OpenCV.

## Architecture

### `skate_analysis.py` — analysis core + CLI

**Where do the files live? (`is_frozen`/`app_dir`/`data_dir`, EXE.md step 1.)** `app_dir()` is the folder with the **bundled** files (the models): next to the scripts, or next to the .exe when the app runs bundled (`sys.frozen`). `data_dir()` is the **writable** folder for what the app creates itself (`%LOCALAPPDATA%\SkateAnalysis`) — an install folder may be read-only. They've lived in `skate_environment.py` since EXE.md step 2 (stdlib-only, so loadable before the splash screen — `data_dir()` is already needed there to redirect the output, while this module pulls in cv2+numpy) and are **passed through** here, since this is the lowest shared module and every existing import has to keep working: `skate_gui` (`_MODEL_DIR`), `skate_yolo` (the YOLO model path, the DirectML export via `_onnx_pad`, the RTMPose file via `_rtmpose_model`) and `skate_db` (`app_version` reads a generated `_version.py` instead of git when frozen, with the same label format) all three use them. In the repo environment they resolve to exactly the same files as before, so nothing about the measurement changes. One behavior change lives in the GUI: bundled, `_load_backend()` does **not** fall back to MediaPipe (that isn't in the package) but returns `_backend_broken` + a blocking message — a fallback would otherwise only show up as an ImportError halfway through the first analysis.

The analysis is a **three-step pipeline**, brought together in **`analyze()`** (returns `(VideoInfo, list[FrameResult])`):

**Step 1 — detection + tracking (`analyze_frames()`, generator).** Per frame, `landmarker.detect_for_video()` runs with **`num_poses` > 1** (default 5): MediaPipe detects *all* skaters in frame. A dedicated **`TargetTracker`** picks the right pose each time: it keeps a torso centroid (shoulders+hips, indices in `TORSO_IDX`), predicts the next position with a constant-velocity model, and links the nearest pose within a distance gate (`TRACK_GATE`). That way tracking doesn't jump to a different skater when they cross. The tracker is **coast-aware**: on a detection gap the prediction shifts along per missed frame (`n x speed`, via `_verwacht()` — with the horizon capped at `hervind_frames` and clamped to the frame; without that the skater would fall permanently outside the gate after ~3 missed frames (motion blur!)) and the gate grows with the gap length (`TRACK_GATE_GROWTH`, capped at `TRACK_GATE_MAX`); without that the skater fell permanently outside the gate after ~3 missed frames. On a match the speed is divided by the gap length, so a gap doesn't inflate the estimate. Seeding happens on a given `doel_punt` (mouse click in the GUI). **Without a click**, `analyze_frames` first watches for `SEED_WARMUP_S` (1 s): those frames are buffered, `_track_candidates` strings them into raw tracks, and `_choose_moving_target` picks the **biggest mover** (median bbox area × distance covered, floor `SEED_MIN_MOVEMENT`) — the counterpart of `MIN_MOVEMENT` in the YOLO backend, since the biggest pose in frame is regularly a bystander along the boarding, not the skater riding further out. That point goes into the tracker as `doel_punt`, after which the buffered frames are played back anyway (no frame is lost; frames before the chosen track's start frame stay empty). After a long loss (`TRACK_LOST_S`) it reseeds — this time at the **separately tracked** last known spot (`laatste_bekend`, apart from the lock flag `centroid`), extrapolated along, and only if someone lies within `TRACK_RESEED_GATE`; otherwise no pose at all (better a gap than a skeleton on a bystander, which gives plausible but wrong angles). The stale click point from frame 0 is thus not reused on a reseed. This step only fills in the raw landmarks (`lm`) + `pose_found` per `FrameResult` — no derivatives yet.

**Step 2 — cleanup + offline smoothing (`smooth_landmarks_offline()`).** Since this is a batch tool (all frames available), we process the whole trajectory per landmark. First, **`_fix_lr_swaps`** repairs left/right swaps of the leg joints: the trajectories are followed for continuity and per frame the assignment with the smallest jump is chosen — in **one joint decision for the whole leg** (knee + ankle on the summed cost, with heel and toe included), because if the knee and ankle decided independently, the left knee could end up hanging off the right ankle: an anatomically impossible skeleton with a nonsensical tibia length (only swap on a *clear* advantage, `LR_SWAP_FACTOR`; a majority vote against the raw detector labels prevents one wrong first frame from flipping the whole sequence — that vote runs **only over the frames where the continuity cost actually gave a verdict** (the `besloten` mask), so the inversion doesn't impose an L/R swap on frames that were skipped precisely because of low visibility) — a persistent swap would otherwise poison the l-r ankle signal of the push-leg cycle. Next, **unreliable frames** are removed: low `visibility` (< `VIS_MIN`), an **occlusion outlier** (Hampel median filter, `_hampel_outliers` — catches e.g. an arm sliding in front of the hip and the joint briefly jumping), or a **bone-length outlier** (`_bone_length_outliers`: the femur/tibia are rigid, a sudden pixel-length jump flags both endpoints as wrong, even if x and y each stay within their own Hampel band). Those get linearly interpolated away (`_interpolate_unreliable`) — but **only short stretches** (≤ `INTERP_MAX_S`, via `_limit_interpolation`): a long unreliable stretch or one at a segment edge keeps the raw detection, because a long straight-line interpolation or a clamped edge would otherwise put the whole skeleton next to the skater instead of on them. On top of that sits a **blur-frame safety net**: if the visibility of most of the data-bearing joints drops below `VIS_MIN` in a single frame all at once (fraction < `BLUR_FRAME_FRAC`), that's a correlated confidence dip from motion blur — not occlusion — and the complete raw detection for that frame is trusted (even if Hampel flagged joints). After that we smooth **bidirectionally/zero-lag** with Savitzky–Golay (`_savgol`, pure numpy — scipy isn't present), per contiguous segment of frames-with-pose (not across detection gaps). This overwrites `resultaat.lm` with cleaned-up, smooth points; jitter disappears while peaks (e.g. full extension) are preserved.

**Step 0 — filtering out interlacing (`deinterlace()`, determined per video by `is_interlaced()`).** A camcorder recording at **1080i50** shoots a *half* frame 50 times a second (first the even image rows, then the odd ones) and weaves those two moments, 1/50 s apart, into one frame. On still parts you see nothing of that; on a moving leg the two halves sit in a different spot — combing. A media player deinterlaces on the GPU during playback, **OpenCV doesn't**: it delivers the woven frame exactly as it sits in the file, so both the image *and* the pose detection see the comb. That's not a cosmetic problem: measured on `00005.MTS`, the two halves sit **6.1 px apart on knees and ankles** (p90 13.4; max 44) against 0.06 px on the progressive phone clips, and with "2 px keypoint error = 2–4° angle error" (RECORDING.md) that's the largest source of noise there is in such footage.

`deinterlace(frame)` throws away the odd rows **wherever the image combs** and interpolates them from the even rows, so the moving part comes from exactly one moment; still parts stay untouched at full vertical resolution. **One field has to win** — the obvious variant, averaging both fields, does remove the comb but leaves the temporal blend in place: measured, the field shift went from 6.07 to 5.52 px that way, against **0.03 px** with this version (ffmpeg's `yadif` gets 0.07 px). Cost **~12 ms per 1080p frame**: negligible next to the ~2 s/frame of the detection pass. For **playback** this is different from what used to be documented here — the 40 ms available at 25 fps also has to cover decoding (~8 ms) and scaling to the screen (~15 ms on a HiDPI panel), and with the original 18 ms that didn't fit: a 1080i recording ran at 53–85% of real speed in the viewing window, visible as slowed-down, jerky playback. Two things fixed that. First, the filter is now written more efficiently, **byte-for-byte the same output**: the merge step goes through `cv2.copyTo` on a contiguous copy instead of `np.where` with a bool mask broadcast over three channels (8.9 → 1.1 ms — OpenCV writes with SIMD across 16 threads, only touching the masked bytes), and `_comb_mask` writes the product into its own temporary array. Watch out when optimizing further: the mask has to keep computing in **int16**. The obvious `cv2.multiply(..., dtype=CV_32S)` isn't just slower (11.8 vs. 5.2 ms) but also gives a *different* mask — int16 overflows on differences above 181, and that wrap-around behavior is baked into the calibration of the 27 clips. Second, the playback loop now counts on the wall clock (see `_play_tick` in the GUI). Verified on both camcorder clips: identical mask, identical filtered frame, and the same `is_interlaced` outcome as before the change, on two progressive clips too.

**`is_interlaced()` measures the field shift, not the comb.** Per frame, the **densest comb cluster** is located — the moving object — and there the even and odd rows are aligned on top of each other with phase correlation. Two cheaper metrics were tried and dropped: aiming at the *median* combed pixel lands on still ice with little motion (6 of 27 clips wrong), and the **comb fraction alone** gives itself away on a small, heavily compressed clip (832×464, 0.035 against ≤0.0025 for everything else progressive) that would then get filtered unnecessarily. Only the shift itself separates the cases, since it's zero by definition if both fields come from the same moment — whatever compression was layered on top. **Calibrated across all 27 videos in the library:** the eleven camcorder fragments measure 1.59–17.41 px, the sixteen progressive clips 0.00–0.15 px; threshold `DEINT_SHIFT` 0.5 px, so ~3x margin on both sides, 0 mistakes. Too few moving frames to judge → False: better not to filter than to touch pixels based on a failed measurement.

The filter hangs off **`open_video(pad, deinterlacen)`**, which returns either a `VideoReader` (comb filter on `read()`/`retrieve()`, the rest via a `__getattr__` passthrough like the DirectML shell) or **literally a `cv2.VideoCapture`** — for progressive material nothing changes, not even an extra Python call per frame. Every read site in both backends goes through it (detection pass, refinement pass, auto-horizon, the CLI's overlay pass, `trim_fragments`, and the GUI player), because **both passes must see the same pixels**: if pass 2 refines on woven footage while pass 1 is filtered, you're measuring two different videos against each other. `analyze(deinterlacen=None)` figures it out itself (CLI convenience); the GUI settles it in the dialog and passes an explicit bool, so the choice is visible and ends up as `deinterlaced` in `settings_json`. **Trimming filters along**: `trim_fragments` re-encodes anyway, so it costs nothing extra there, and the fragment is clean everywhere afterward — even in a player that doesn't deinterlace itself. Verified that a fragment trimmed that way no longer counts as interlaced under `is_interlaced`, so nothing gets filtered twice anywhere.

**A/B on `00005 11-23.mp4`** (177 frames, the same target click and horizon, `bocht=False` so both runs see exactly the same frames). The bone-length CV is the measure that counts here: femur and tibia are rigid, so whatever remains of their pixel length around the trend is measurement noise on the keypoints.

All four bone lengths become **two to two-and-a-half times more stable** and the jitter drops by a quarter — exactly the pattern you'd expect when a systematic position error is removed from the measurement points. The joints shift by a median of 4.5–6.0 px (p95 19–37), which matches the 6.1 px field shift that was removed. One push that used to be `INCOMPLETE_TRUNCATED` now yields a full measurement (38.9°), so five usable angles instead of four.

**Two things that need to be stated honestly.** Coverage drops by 2 frames (164 → 162) — the filter interpolates away half the image rows on the moving part, and every now and then that costs a detection. And `CV stance_l` goes 0.179 → 0.221, against the trend of every other bone measurement; the left stance run also happens to be the run that changes shape (push 4 ends on frame 147 instead of 155 and goes from 46.9° to 54.5°), so that number doesn't run over the same frames and isn't a clean comparison. **What does *not* follow from this is a golden angle error**: these are proxy metrics without ground truth. Anyone who wants to know how many degrees are really gained needs to run `skate_eval.py annotate` on this material.

**Step 2b — corner detection (`determine_corner_sequence()`, on by default; `analyze(..., bocht=False)` or CLI `--no-corner` turns it off).** In the corner the skater isn't facing the camera, so there's nothing meaningful to measure there — and those frames are the most expensive part of the analysis. The signal is **`corner_ratio(lm, w, h)` = hip width / torso length** (shoulder midpoint→hip midpoint), in pixels: scale-free like `_extension_ratio`, and specifically sensitive to the rotation around the vertical axis that the corner produces (facing the camera, the hips sit side by side; in the corner, front to back; while the torso stays the same length). **Measured across all 22 analyses in the library:** 18 straightaway clips never drop below 0.57 (median 0.75–1.20), the corner section of four long TV clips sits at 0.21–0.24 — margin over 3x; alternative denominators (femur, whole leg, shoulder width) gave 1.7–2.7x. `determine_corner_sequence` follows the recipe of `determine_horizon_sequence`/`box_sequence`: Hampel outliers + gaps removed → Savitzky–Golay over `CORNER_SMOOTH_S` → **hysteresis** `CORNER_IN` 0.40 in / `CORNER_OUT` 0.50 out (the `STANCE_BAND_FRAC` pattern) → runs shorter than `CORNER_MIN_S` cleared (`_clear_short_runs`, in both directions: a few "straight" frames in the middle of the corner isn't a straightaway either). Frames without a pose inherit the running state and keep an already-set flag; frames with a pose are judged on their own ratio and can thus also **clear** the flag — that's what makes an incorrect runtime skip in the YOLO backend self-correcting. Below `CORNER_MIN_TORSO_PX` (12 px) the ratio is pixel noise and the frame counts as unmeasurable (the farthest skater in the library measures 25–35 px).

The **exclusion itself is one line** in step 3: a corner frame gets no `lm_data`. Leg assignment, push completion and event segmentation all build their segments on "pose and `lm_data`", so they simply see the corner as a detection gap — nothing about the measurement logic changes. `draw_all_landmarks` reads `r.lm`, so the skeleton stays visible with "CORNER — not measured" next to it (`draw_overlay_on_frame` returns right after; `draw_leg_overlay` has an `lm_data is None` guard). **Flagged, not hard-cut**, because some clips actually start *in* the corner (the last strokes of the previous lap) and a video with multiple laps thus still yields every straightaway. `FrameResult.corner` travels along in the npz (old npz's without that key still load unchanged): the YOLO backend's runtime skip can't be recovered from the landmarks, so it has to be preserved.

**Step 3 — derivatives (`process_derivatives()`).** After smoothing, the derived quantities are computed per frame from the smooth `lm`:
1. **`get_landmarks()`** → pixel coordinates (hip, knee, ankle, heel, toe — left/right) — **not** on a corner frame (see step 2b).
2. **Push-leg assignment** — by default **cycle-aware** (`assign_push_leg_cyclic`): the ankle height difference (left − right) is an oscillator that moves along with the stroke; that signal gets smoothed and turned into a leg with **hysteresis** (`STANCE_BAND_FRAC`), so it only switches on a genuine weight transfer (no per-frame flicker). Per contiguous pose segment. The old per-frame `determine_push_leg()` (lowest ankle + hip-shift tiebreaker) remains as a fallback (`cyclus=False`).
3. **`calculate_angle_to_ice()`** → push angle (ankle→knee relative to the ice), plus `smooth_hoek` (`_set_smooth_angle`: **centered**, zero-lag average over `--smooth` frames, per contiguous run of the same stance leg — purely for HUD/graph; the table uses the angle of a single frame). The **horizon/camera tilt** is subtracted here from the measured angle, so a tilted or wobbling camera doesn't pollute the push angle. The correction sits **per frame** in `r.horizon_deg`, set by **`set_horizon()`** (called by `analyze` after smoothing, shared by both backends):
   - **Fixed** (`horizon_deg`, default 0): one manually set angle, broadcast everywhere. Source: a drawn reference line (GUI: `HorizonPicker` → `horizon_angle_from_line()`) or a one-off detection on a single frame (`detect_ice_line()`, Hough on the bottom of the image).
   - **Auto per frame** (`auto_horizon=True`, GUI checkbox "Automatic per frame" / CLI `--auto-horizon`): **`determine_horizon_sequence()`** runs `detect_ice_line()` on every frame (a separate video pass) and turns it into a stable signal — detection gaps and wrong lines (Hampel) interpolated away, then Savitzky–Golay over `HORIZON_SMOOTH_S` — so the horizon follows the slow drift without per-frame Hough jitter. This second pass shares the progress bar with the detection pass (each gets half) via **`phase_progress()`**, so it stays one continuous bar; applied in both backends.

   It's only a subtraction; for large tilts (>~10°) you'd have to rotate the landmarks first. The drawn white ice line in the overlay tilts along per frame (`draw_overlay_on_frame`/`draw_leg_overlay` read `resultaat.horizon_deg`).
4. **Push completion** — by default from **leg extension** (`determine_push_from_extension`, `afzet_strek=True`): "leg fully extended = push complete". Per contiguous stance run (`r.been` constant), the **extension ratio** `_extension_ratio` = |hip→ankle| / (femur+tibia) is calculated — a **scale-free** signal in [0,1] (~1 = extended), so no fixed pixel/angle threshold is needed and it doesn't matter whether the skater is close or far away. The signal is smoothed with Savitzky–Golay (`EXTENSION_SMOOTH_S`). But the leg is "extended" for a whole phase: from **standing up** after the plant (leg ≈ vertical → lower-leg angle ~80-90°) to full **sideways push** (leg flat → ~50°). The extension maximum falls on the standing-up part (a misleadingly high angle), so the push angle isn't read off the `argmax` but within the **extended phase** — the contiguous plateau around the extension peak where the ratio stays within `EXTENSION_PLATEAU_BAND` of its maximum — at the frame with the **flattest (lowest) lower-leg angle** (`calculate_angle_to_ice`); standing up (high angle) thus drops out automatically and the recovery already sits outside the plateau. `r.gewicht_erop` is True through that frame, False after, so the event spans the whole load+push and ends on the flattest-angle frame (`PushEvent.angle`; `max_angle` then shows the standing-up part as the top of the range). **Predictable stroke duration as a soft prior**: the median run length gives the half-stroke period; a run shorter than `EXTENSION_MIN_STROKE_FRAC` of that is almost certainly a noise flip of the leg assignment and yields no push (prevents phantom pushes). That median only runs **over runs of at least `EXTENSION_MIN_RUN_S`** (0.2 s — a half stroke can't be shorter): had the noise runs taken part, the median — and so the threshold — would have dropped exactly when there are many L/R flips, exactly when you need it most (BUGS.md A3; on `1edc50ac` `min_run` went from 5 → 11 frames). **Incomplete runs** get `FrameResult.push_incomplete` (a reason text, not a boolean — see `INCOMPLETE_*`), which carries through to `PushEvent.incomplete`: the event stays visible (after all, something happened), but falls outside avg/min/max in the GUI and outside `AVG(angle)` in the library list. One flag with a reason instead of two booleans, since every filter site only has to check for truth while the GUI tooltip can tell the user *what* was wrong. Two reasons:
   - **`INCOMPLETE_TRUNCATED`** — a run that doesn't end on a leg switch but on the end of the video or of the pose segment only contains the first half of the push; the "flattest angle" there is actually the standing-up part (measured: +15 to +25° too steep, and that happened in 18 of 18 saved analyses — BUGS.md A2). A run that's truncated at the *start* of a segment counts fine — only the load phase is missing there, the push completion is still in frame.
   - **`INCOMPLETE_NO_PUSH`** — the run is long enough and ends cleanly on a leg switch, but the extension plateau only covers the standing-up phase, so even the flattest angle within it is the standing-up part (74–83°). Recognized by the geometry: if the lower leg is less than `EXTENSION_MIN_SLOPE_DEG` (20°) out of vertical at "completion", there was no sideways push — sin(20°) ≈ 0.34. Occurred in 3 of 100 events in the library (BUGS.md R1); the steepest healthy measurement is at 66.7°.

   The ratio ends up per frame in `FrameResult.strek_ratio` (HUD/GUI live status). Requires the cycle-aware leg assignment.
   - **Old weight vote** (`afzet_strek=False`, or `cyclus=False`): **`detect_weight_on_leg()`** combines 3 signals (ankle rises, knee >162°, hip shifts away above `--threshold`) — with 2+ signals the weight counts as "off". This function also runs in extension mode (yields `kniehoek` + the 3 signals as HUD diagnostics), but no longer determines `gewicht_erop` there.

Importantly, the derivatives are therefore no longer calculated during the detection pass, but afterward, so everything rests on the smoothed landmarks. The CLI (`analyze_video()`) is therefore **two-pass**: first `analyze()` (detection+tracking+smoothing), then the video is read again to draw the overlay and write it out. The GUI caches the `FrameResult` list and draws live while playing/scrubbing.

**Drawing functions** (`draw_all_landmarks`, `draw_leg_overlay`, `draw_hud`, bundled in `draw_overlay_on_frame()`) put everything on a single frame: full skeleton lit up in the background, the push leg highlighted thick (green = weight on, red = push completed) with an angle line, and a HUD panel top-left with time/angles/status. `draw_overlay_on_frame()` has an on/off flag per layer (`toon_skelet`/`toon_afzetbeen`/`toon_hud`) and is shared by the CLI and the GUI.

**`segment_pushes()`** groups the per-frame results into `PushEvent`s: contiguous frames in which the same leg is the push leg and the weight is still on it (`gewicht_erop`). An event's angle is the angle **of the completion frame itself** (`r.hoek` on the last frame of the run — exactly the frame `determine_push_from_extension` picked as the flattest angle), not an average: a trailing average over a falling angle structurally gave angles that were too steep (up to +10°, BUGS.md A1). `min_angle`/`max_angle` come from that same per-frame run, so the table uses one definition of "the angle" throughout. An event inherits `incomplete` from its frames (see step 4): it's shown in the table (gray, with a tooltip explaining the reason) but not in the statistics. This is the data source for the table in the GUI.

**Alternation feedback (`force_alternating()`, on by default in `segment_pushes`).** Skating is always L-R-L-R, so two same-leg events in a row is impossible. For each such pair, the gap between them is inspected: was the other leg *not* the push leg there and is the gap small → **push that got split apart, merge** (`_merge_events`, `note="merged"`); was the other leg briefly *the* push leg there (that short push filtered out by `min_lengte`) or is the gap large → **missed counter-push, flag it** (`note="missed counter-push?"`, not silently erased). The GUI colors flagged rows and counts them in the statistics. `PushEvent.note` carries this status.

State between frames (needed for the heuristics) is kept in `process_derivatives()` in `deque`s with a fixed maxlen: `enkel_hist` (per leg, 10 frames) and `heup_hist` (10 frames); on a detection gap those are cleared so nothing gets compared across the gap. (`_set_smooth_angle`'s centered average no longer uses a trailing deque, unlike an earlier version of this file.)

**Tuning constants** (module-level in `skate_analysis.py`): `NUM_POSES_DEFAULT` (max. number of skaters to detect), `TRACK_GATE` (max. normalized jump per frame before the tracker "coasts" instead of jumping) + `TRACK_GATE_GROWTH`/`TRACK_GATE_MAX` (gate growth per missed frame + ceiling), `TRACK_LOST_S` (loss duration before reseeding) + `TRACK_RESEED_GATE` (max. distance to the last known spot on a reseed), `SEED_WARMUP_S`/`SEED_MIN_MOVEMENT` (warmup window of the cold start without a click + floor below which a candidate counts as a stationary bystander), `SMOOTH_WINDOW_S`/`SMOOTH_POLY` (Savitzky–Golay window length in seconds + polynomial order), `EXTENSION_SMOOTH_S`/`EXTENSION_MIN_STROKE_FRAC`/`EXTENSION_MIN_RUN_S`/`EXTENSION_PLATEAU_BAND` (extension-signal smoothing + minimum stance run as a fraction of the half-stroke period + absolute floor (s) for the runs the stroke period is estimated from + width of the extended plateau within which the flattest lower-leg angle counts as the push angle), `CORNER_IN`/`CORNER_OUT`/`CORNER_SMOOTH_S`/`CORNER_MIN_S`/`CORNER_MIN_TORSO_PX` (corner detection, see step 2b). CLI flags: `--num-poses`, `--heavy` (uses `pose_landmarker_heavy.task`), `--target X,Y` (normalized start point), `--no-smooth`, `--no-corner`.

`POSE_CONNECTIONS` (module-level) is now hardcoded, taken from `mp_vision.PoseLandmarksConnections.POSE_LANDMARKS`, and is used to draw the skeleton, since the Tasks API no longer has a ready-made `draw_landmarks()` helper like the old Solutions API.

**`trim_fragments(bron_pad, fragmenten, doelmap, ...)`** (phase 8, separate from the pipeline) writes marked stretches of a long recording out as separate clips. `fragmenten` = `(start, end, name)` with **both bounds inclusive** and **exactly on those frames** — no margin added or removed (the trainer sets the bounds themselves while marking; see ROADMAP phase 8). **One sequential pass**: every frame goes to the writer of every fragment it falls in, so the video is decoded exactly once and there's **no seeking anywhere** — same motive as `_detect_all`'s own read loop, and overlapping fragments therefore cost nothing extra. It stops as soon as the last end frame has passed (a fragment near the start of a half-hour recording thus costs almost nothing), and frames that fall in no fragment at all are only advanced with **`grab()` without `retrieve()`** (~3 ms instead of ~9 ms) — for a fragment far into a long recording that fast-forwarding is the lion's share of the work. Measured: trimming 10 s at minute 20 of a 23-minute recording = 96 s, with a `QProgressDialog` (`wasCanceled` as `stop_check`) around it; negligible next to the analysis that follows (~2 s/frame). Codec `mp4v` (comes with the opencv-python wheel; `avc1` is often missing on Windows), so it's **re-encoded**. Frame-exact aligned (no off-by-one, verified on a synthetic sequence), and the A/B on "Schaats frontaal.MOV" trimmed from itself gave **the same coverage, the same six pushes, and the same L-R order**, with angle differences up to 1.2° (usually ≤ 0.5°) and 1–2 px median on the joints. An ffmpeg stream-copy would avoid the re-encode but can only start on a keyframe — exactly the silent margin that isn't wanted here. `stop_check`/`progress_callback` for the progress dialog; on abort (`TrimAborted`) or an error the half-written files are cleaned up, and a fragment that lies entirely past the end of the video gives an `IOError` instead of sending a nonexistent path into the batch flow.

### `skate_yolo.py` — YOLO-pose + ByteTrack backend with offline target selection

An alternative **detection+tracking step** that replaces step 1 of the MediaPipe pipeline; step 2 (offline smoothing) and 3 (derivatives) from `skate_analysis.py` are reused. `analyze()` has a **signature-compatible** interface with `skate_analysis.analyze()` (the MediaPipe `model_pad`/`num_poses` arguments are ignored) and returns `(VideoInfo, list[FrameResult])`.

Since this is a batch tool, target selection happens **offline/globally** instead of streaming per frame — that's the core of the robustness:

1. **Detection pass at high resolution (`_detect_all`, `DETECT_IMGSZ`=1280).** `model.track(frame, persist=True, tracker='bytetrack.yaml', imgsz=1280)` per frame; *all* people are kept as `Detection` (ByteTrack ID, centroid, bbox, area, MediaPipe-33 landmarks, and a torso color histogram). At the default 640, far-away/motion-blurred skaters simply aren't detected at all (on the test video: frames 0–3 fully missed) — at 1280 they are. Costs ~2 s/frame on CPU with yolo26x-pose (a bit faster than the older yolo11x-pose, and better on blurry frames/occlusion).

   **The loop reads the frames itself** (`cv2.VideoCapture` + `model.track(<numpy frame>)`) instead of letting `model.track(source=pad, stream=True)` stream. Reason: only this way can a frame be read but not inferred, and that's exactly what **`_CornerGuard`** does in the corner. Every frame is read (decoding is negligible next to ~2 s of inference), so the frame numbering stays exactly the video's own. `_detect_all` returns `(frames, excluded)`.

   **`_CornerGuard` — the time savings.** The detection pass is ~94% of the analysis time and yields nothing in the corner. The guard judges every inferred frame by its detections: *straightaway* (someone with `corner_ratio` ≥ `CORNER_OUT` who's also *moving*) → straight back to full speed; *turned* (someone measurable, but `corner_ratio` < `CORNER_IN`) → skip after `CORNER_START_S` (0.5 s); *nothing* (nobody measurable) → only after `CORNER_STILL_S` (**3.0 s**, deliberately above the longest detection gap on a straightaway in the library: 2.1 s on IMG_9001, a blur gap must not push the analysis into skip mode). In skip mode, inference only runs every `CORNER_CHECK_S` (0.33 s ≈ 10 frames at 30 fps, but fps-independent). The **movement requirement** (`CORNER_MIN_MOVEMENT`, per ByteTrack ID over `CORNER_MOVE_WINDOW_S`) keeps bystanders along the boarding out of the "straightaway" vote — they stand facing the camera and would otherwise keep the analysis at full speed forever (same motive as `MIN_MOVEMENT` in target selection). Both displacement **and growth** count: a skater heading straight at the camera barely moves in frame but grows ~18%/s. A track with too little history gets the benefit of the doubt.

   **Measured** on "Kim tempo" (888 frames, 52% corner): 2266 s → **1253 s** (45% faster). With `bocht=False` the own read loop gives a **byte-identical** result to the saved analysis that was still made with `model.track(source=...)`, and on a clip without a corner ("Schaats frontaal", "7e ronde") nothing changes.

   **A check frame is a peek, not a measurement.** In skip mode every `CORNER_CHECK_S`th frame does get inference and thus a skeleton — but the neighboring frames that would together prove a push are precisely the ones skipped, so such a frame must never yield an angle. `_detect_all` therefore returns `(frames, out_of_measurement)`, containing **both the skipped frames and the check frames**, and `_corner_with_check_frames` sets `bocht=True` on everything in it after each classification. A check frame's *verdict* does still count (it may end the corner — that's what it's there for), only its own measurement doesn't. Without that rule such a frame could clear itself on its own hip stance: mid-corner a skater occasionally turns briefly almost frontal (visible in the Ellia and Fran clips). Costs at most the first frame of the next stance run, and a run truncated at the *start* counts anyway.

   **Why this is safe:** the refinement pass fills detection gaps up to `GAP_FILL_S` (1.0 s) and the gaps skip mode leaves behind are 0.33 s. That's why the corner is **determined on the raw pass-1 landmarks, before refinement** (`_corner_with_check_frames` runs twice: once here, once more on the refined landmarks). If the guard wrongly skipped a stretch, the next check frame within `CORNER_CHECK_S` reports a straightaway skater and the detection pass immediately goes back to full speed — so at most one check interval is lost; too little skipping costs time, too much skipping costs (almost) no coverage. Conversely, `_interpolate_target(..., bocht=...)` keeps gap-filling *out* of the corner stretches, so pass 2 doesn't eat back the time saved.
2. **Suit color (`_torso_hist`, `ColorReference`).** HSV histogram (`COLOR_BINS` 8×4×3, L1-normalized) of the torso polygon (shoulders→hips; fallback: upper bbox), compared with 1 − Bhattacharyya (`_hist_sim`). Validated on the test video: the target skater scores 0.54–1.0 against their own reference, the other skater ≤ 0.34. The reference is a running average of the last `REF_HIST_N` target histograms (absorbs scale/lighting changes without being able to drift onto someone else). **Origin matters**: `_torso_hist` returns `(hist, from_mask)` and `Detection` carries that as `hist_mask` (+ property `ref_hist`). A bbox fallback contains background (ice, boarding, spectators) and so isn't comparable with a mask histogram; such histograms don't feed the reference, may not cut a tracklet, and may not reject an estimate in the refinement passes. In stitching they count as "uncertain": no color threshold, but a half-width distance gate.
3. **Tracklet splits on color (`_split_by_color`).** ByteTrack regularly "steals" the other skater's ID when skaters cross (on the test video: ID 4 silently switched from the black skater to the white/red one around frame 32). So every tracklet gets cut where the suit color drops below `COLOR_SPLIT_MIN` for `COLOR_SPLIT_N` consecutive frames; short dips (occlusion mixing) survive. Frames without a mask histogram give no verdict at all: they don't count toward the cut, but don't reset the counter either.
4. **Seed (`_choose_seed`).** With a mouse click: chronologically the first tracklet whose bbox contains the click point (with multiple hits, first a tracklet of at least `SEED_MIN_LEN` detections — a 1–2 frame fragment gives too thin a color reference), searched over the first **`CLICK_SEARCH_S` (6) seconds**; if nobody sits on the click in any of those frames, the detection that stood closest *next to* it wins instead, within a gate of `CLICK_GATE_BASE` + `CLICK_GATE_GROWTH` per second elapsed. Without a click: the **biggest mover** — median area × path length, with `MIN_MOVEMENT` as a floor — so a stationary bystander along the boarding (who can be *bigger* in frame than the far-off skater) is never chosen. Returns `(tracklet, click_missed)`: if the click hit nobody, the biggest mover is followed silently instead — possibly the wrong skater — and a message goes to the GUI via `waarschuwing_callback`. **That 6 s search window isn't generosity, it's the measured reality**: the click sits on frame 0, but a skater who starts far away is still too small there to be detected. On `00005 8-41` they only appeared on frame 84 (**3.4 s**) — with the old 60-frame window the click thus fell outside the search's field of view, the trainer got the message "your click couldn't be linked", and clicking seemed to do nothing. Verified on the dumped detections of that same clip: the click lies **within** the intended skater's bbox on frame 84 (distance 0.000), the new seed yields exactly the same chain as the old fallback (197 frames, 27–280, 4 gaps) and only the warning disappears. There the fallback happened to catch the same skater; the moment it doesn't, the click now decides. **Deliberately no constant-velocity extrapolation back** to the click frame like `_stitch_chain` does over its gaps — over that many seconds that model doesn't hold: the torso sways sideways with every stroke (measured x between 0.33 and 0.50 while net position barely moves), and a velocity from five frames places the skater, extrapolated back, at x = −0.001 to −1.563, well off-frame. The position in frame is the trustworthy signal here. Self-test: `_self_test_seed` in `python skate_yolo.py`. If target selection yields nothing at all (not a single tracklet), `analyze()` **raises** instead of producing an empty analysis that lands in the library as "0 pushes". **With a drawn box** (`doel_kader`, see the spyglass below), two more rules apply: a candidate may be at most `BOX_SIZE_MAX` (3x) as tall as the box — the user indicated the skater's size, so a bystander four times that size sitting on the click isn't who was meant (on `00005 8-41` a crowd of large skaters stands on the right while the intended skater is on the left, starting at ~100 px) — and with a box, `_choose_seed` **doesn't** fall back to the biggest mover itself (`(None, True)`). `analyze` does that fallback afterward anyway, alongside the spyglass from the box, and reports it with the frame number where the mover starts: the box may never turn out worse than a click. That's not theory — on `00000 16-14` (skater 35–57 px, only detected on frame 187 of 200) the spyglass alone gave one frame, while the fallback picks up the detections at the end. Such a fallback chain is a second guess, not a confirmation of the box: the spyglass then gets `chain_linked=False`, see there.
5. **Chain stitching (`_stitch_chain`).** Starting from the seed tracklet, tracklets are strung together forward and backward. A candidate only counts if (a) the suit color matches the reference (≥ `COLOR_MATCH_MIN`) and (b) its joining position lies within the gate of the constant-velocity extrapolation over the gap (`STITCH_GATE_BASIS` + `STITCH_GATE_GROWTH`·gap — a skater's direction of travel is predictable). **Of the usable candidates, the smallest gap wins**, not the highest score — and that isn't a matter of taste. The chain grows in small steps, and whoever jumps over an intermediate tracklet makes that tracklet **unreachable**: it then sits in the middle of the chain and no longer extends it in either direction. The old rule (`sim − 0.5·dist/gate`) divided the distance by a gate that grows *with* the gap and thereby rewarded exactly that jump: on `00005 14-48`, 66-182 (gap 35, color 0.72, score 0.701) beat 41-66 (gap 10, color 0.71, score 0.642), after which 41-66 never made it in and a 34-frame gap remained — just too big for `GAP_FILL_S` (1.0 s = 25 frames), so 34 frames with no skeleton. Color and distance are gates; on an equal gap, the old score decides. Further: color is measured on the **side that touches the chain** (`t[:10]` forward, `t[-10:]` backward — lighting and scale are most comparable there); a candidate may **overlap** the chain (around an occlusion, two IDs coexist for a while) provided it nearly coincides with the chain on the shared frames (`STITCH_OVERLAP_GATE` 0.05). That check is needed because a clip contains tracklets that span the **entire** clip — stationary bystanders along the boarding, `path` ≈ 0.1 — and those would otherwise slip in via an overlap; measured, they get rejected at 0.13–0.57. Two detections in the same frame are by definition two different boxes, so coinciding means the same skater under two IDs, and that's a sharper test than any extrapolation over a gap. Duplicate frames get thinned out on color at the end. And a **short seed** first gets padded by `_bootstrap()` on position alone up to `SEED_MIN_LEN` (gap ≤ `BOOTSTRAP_MAX_GAP`), since with a single histogram there's nothing yet to test against.
6. **Refinement pass (`_refine_landmarks`, `verfijn=True` default).** The video is read again; per target frame the pose is re-estimated with the skater filling the inference image → substantially more accurate keypoints (and so angles). Detection gaps ≤ `GAP_FILL_S` get an interpolated bbox and are thereby filled in too. Two routes:
   - **RTMPose-26 (`_refine_rtmpose`, active if rtmlib is importable — `IS_RTMPOSE`).** Top-down on the target bbox with `rtmpose-x` (Halpe26, `RTMPOSE_MODEL`, SimCC = subpixel decoding, ~76 COCO-AP — more accurate than the yolo26x-pose detection pass) via ONNXRuntime — also considerably faster than the YOLO-crop route on CPU. Yields **real heel/toe keypoints** (`_halpe26_to_landmarks`: Halpe 20/21→MP 31/32, 24/25→MP 29/30). Quality gates: average leg keypoint score ≥ `RTMPOSE_MIN_SCORE` (otherwise legs not seen → keep pass-1), and the **color gate** — torso histogram of the estimate vs. the reference: on a real detection, only a clearly different suit (< `COLOR_SPLIT_MIN`) is rejected, a gap frame requires a positive match (≥ `COLOR_MATCH_MIN`) instead, since there's no pass-1 safety net there. This also measures the **midline quality flag** (`_midline_deviation` → `FrameResult.midline_dev`, serialized in the npz): filmed frontally, the knee should sit horizontally in the middle of the leg; the deviation from the midline of the color mask flags shaky frames. The color comes from a **thigh self-sample of the same leg in the same frame** (`_leg_hist`), not from the torso reference — a suit is often two-toned (white torso, black pants), but the thigh and knee are always the same fabric. **Pitfall:** `cv2.calcBackProject` returns uint8 — the histogram has to be normalized 0–255 (NORM_MINMAX); with an L1 histogram (values ≪ 1) everything truncates to 0 and the mask stays empty. Deliberately only a measurement, no automatic correction yet, until it's shown to actually improve the angles.
   - **YOLO-crop fallback (`_refine_yolo_crop`, without rtmlib).** Square crop (`REFINE_MARGIN` × bbox, min. `REFINE_MIN_PX`) through `model.predict(imgsz=REFINE_IMGSZ)`; `_choose_in_crop` uses the color reference as a gatekeeper; without a color match, only a candidate almost exactly at the expected spot is accepted, otherwise no refinement at all (the pass-1 landmarks stay in place).

7. **Spyglass (`_Spyglass`, opt-in via `doel_kader`) — following a too-small skater.** The detection pass only picks up a skater from about **80–130 px tall** (measured across the 48 analyses in the library, 1080p): on `00005 8-41` they're already ~100 px in frame at frame 0 but the first detection only comes on frame 84–112 (3.4–4.5 s), and on `00005 10-57`/`14-48` the pose is missing on 84/132 and 100/183 frames respectively — skater ~90–100 px, a crowd of large skaters in front of them. The refinement pass does work on such a skater (RTMPose crops the bbox and scales it up to 288×384; every frame from the first detection onward in those clips is refined that way), so the problem is **finding the bbox**, not the keypoints. If the user draws a box around the skater in `TargetPicker`, that gives the bbox on frame 0, after which the spyglass propagates it **frame to frame from its own refined keypoints** (`_bbox_from_lm` + constant velocity), in `_refine_landmarks`'s loop. **Deliberately no second detector**: a YOLO crop would either cost a second model instance (VRAM on the 4 GB laptop) or a `model.predict` during the `track()` session — and that feeds ByteTrack with crop coordinates, since `track()` registers callbacks on the model that keep firing on every `predict()` (checked in ultralytics 8.4.89). RTMPose on the previous bbox costs ~30–100 ms and uses what's already there. What the spyglass fills in: the run-up before the first detection, gaps longer than `GAP_FILL_S` (the shorter ones stay interpolated, as before), the tail, and the stretches `_CornerGuard` had skipped — it ignores the `bocht` flag, since propagation is cheap and whether a filled frame is a corner is decided afterward by the ratio anyway. Four safety nets, since RTMPose **always** produces a skeleton, even if someone else has slid into the bbox: the score gate (`RTMPOSE_MIN_SCORE` on the legs), the **veto color gate** (`_refine_rtmpose(poort='veto')`: only a clearly different suit, < `COLOR_SPLIT_MIN`, gets rejected — the torso of a 90 px skater is ~15×25 px, too noisy for the positive `'match'` threshold gap frames require), **plausibility per step** (`SPYGLASS_JUMP`/`SPYGLASS_GROWTH`: jumping more than half a body height or growing ×1.5 in one frame is a mix-up, not a skater), and the **link test**: hits stay `pending` until the run touches the chain, and then the IoU of the predicted bbox with the chain bbox (`SPYGLASS_LINK_IOU`) decides whether the whole run is accepted or rejected. If a run dies (`SPYGLASS_COAST_S` without a hit) or the video ends, the **origin** decides: a run starting from a chain frame is accepted (the identity came from a verified point), a run starting from the box only if the chain isn't demonstrably the same skater (`chain_linked=False`: no chain, or the biggest-mover fallback — then box and chain are two separate guesses about different stretches of the clip). If the chain *was* found via the box, then a box run that doesn't reach it is suspect: a hand-drawn box isn't proven identity. `anchor` restarts the run on every chain frame (a fresh velocity for the coast), `follow` only takes interpolated frames along as position. On the first step of a box run, `SPYGLASS_START_SCALES` (0.7/1.0/1.4×) are tried and the highest leg score wins: a hand-drawn box is rarely tight. Spyglass hits **don't feed the color reference** (that's the chain color, used for the chain frames even after the run-up), except in spyglass-only mode (no seed, see `_choose_seed`), where the spyglass bootstraps its own reference. A filled frame gets **un-marked** in `excluded`: it *has* been analyzed, so the second `_corner_with_check_frames` judges it on its own hip stance — a filled frame in the middle of a real corner just becomes a corner, `_clear_short_runs` cleans up stray "straight" flashes. If spyglass-only also yields nothing, the existing `RuntimeError` with a hint about the box. **Opt-in via the box**, and that's not laziness: without a box, behavior is byte-for-byte as before, since the spyglass would otherwise also fill in every analysis's gaps > `GAP_FILL_S` and corner skips — a change in measurement that needs to be measured separately first. The refinement functions are a callable (`estimate`), so `_Spyglass` is pure state and is tested without video or model in `_self_test_spyglass` (link correct/wrong, coast shorter/longer than the limit, box run with and without a chain, plausibility). Every run writes a `[spyglass]` line to the log (frames, origin, accepted/rejected + reason), and the outcome of the box run (`box_outcome`) goes to the user as a warning if that run didn't reach the chain ("…{n} frame(s) able to follow ({reason})") — the difference between "0 pushes" and knowing why.

**The floor: below ~70 px there's nothing to measure, with any finder at all** (`BOX_MIN_HEIGHT_PX`, only a warning when drawing such a box). Measured on `00000 16-14` (a Bochum recording, camera at the end of the straightaway): the skater is 35–57 px tall for 7.5 of 8 s, dark suit against dark boarding, in a deep crouch. RTMPose on the hand-drawn box (and on the three starting scales) gave **leg scores of 0.09–0.24** with fewer than four keypoints above 0.3 — the 0.3 gate correctly rejects that; only on frames 32–35 did it briefly reach 0.35–0.44, and then the skeleton extent is 34–38 px, legs of ~15 px. YOLO on a 256-px crop around the box at `imgsz` 1280 (5x magnified) only occasionally saw a blob (conf 0.3–0.6, mostly the people at the boarding), and its keypoint scores say nothing (always 0.95+). The detection pass itself only saw them on frame 187 at 137 px. Outcome with every safety net: 9 frames (17 and 192–199), 0 pushes — and three messages (box too small, chain couldn't be linked + mover followed from frame 192, spyglass lost on frame 43 after 1 frame). The answer on such a clip isn't a better finder but a different fragment: start where the skater is ~80 px (here 16:21 instead of 16:14). That's also why the box instructions in INSTALL.md mention that floor. **A higher detection resolution was measured on the same clip and rejected**: `imgsz` 1920 finds them at ~73 px instead of ~115 px (frame 144 instead of 187), 2560 not earlier but more stable, and below 73 px at no resolution at all — against 2.0x resp. 3.2x the detection pass (0.94 → 1.92 → 3.05 s/frame on DirectML). The band that 1920 adds is already covered by the box at 1280; `DETECT_IMGSZ` stays 1280.

The progress bar splits the passes (detection / refinement / possibly auto-horizon) into equal slices via `phase_progress`. Result on the test video ("Schaats frontaal.MOV", two crossing skaters + bystanders): 100% pose coverage and perfectly L-R-alternating push events, where the old streaming ID follower had detection gaps and a skater swap.

**Measured effect of the nearest-first rule** (`00005 14-48`, 183 frames): coverage **74.3% → 92.9%**, 12 → 13 pushes, alternation errors 3 → 2, stance-leg bone-length CV 0.070 → 0.052, jitter 4.82 → 4.49 px/frame². **Not a single existing angle shifted**: eleven of the twelve are identical, median 0.0 px on knees and ankles in the shared frames. What disappeared is one push flagged as `incomplete` at 58.0° — an artifact of the gap, since the stance run broke off on it — and in its place there are now two full pushes (51.5° and 37.7°). That's the pattern to watch for in this kind of work: a gap doesn't just cost coverage, it **fabricates a too-steep measurement**, and fortunately that one was already excluded from the average as `INCOMPLETE_TRUNCATED`. **Checked that this is purely additive**: the same tracklets through the old and the new `_stitch_chain` (an offline replay on a captured dump, so only these two hunks differ) gives on `00005 14-48` 118 → 138 chain frames where **not a single frame disappears** and of the 118 shared frames exactly one gets a different detection — frame 66, the join point, where the deduplication picks the best color match. On the reference clip "Schaats frontaal" the outcome is **bit-identical** (83 chain frames, the same detections): where there's nothing to gain, nothing changes either. Watch out when consulting older analyses: the saved "Schaats frontaal" from 19 July does differ from a fresh run, but that comes from the pipeline changes in between — not from this fix — and that exact confusion is the reason to do such an A/B on a dump instead of against a saved npz.

**Limit of color-based target selection: two skaters in the same suit.** The whole target-selection machinery — `ColorReference`, `COLOR_MATCH_MIN`, `COLOR_SPLIT_MIN`, `_split_by_color` — assumes the suit color distinguishes skaters. If a team skates in identical suits one behind the other, that machinery gives **the same answer on every pair**, and target selection silently falls back to position alone; an ID theft by ByteTrack then also no longer gets cut by `_split_by_color`. Nothing warns about this situation, so keep it in mind when judging an analysis. `00005 14-48` is such a clip (two skaters in the same suit, one behind the other) and is therefore a poor candidate to validate a tuning change against — verified that the frames the nearest-first rule adds there are in fact the right skater (in every added frame exactly one plausible candidate, the nearest other moving skater 0.13–0.17 image widths away, and the bbox area matches the neighboring frames), but that's luck of this clip, not a property of the method. **This is at the same time the strongest argument for the nearest-first rule**: without a color verdict, a small gap is the only protection left, since the shorter the jump, the less the constant-velocity prediction can drift — and the old rule chose the big jump instead.

- **COCO-17 → MediaPipe-33 mapping** (`COCO_TO_MP` in `_coco_to_landmarks()`): shoulders/elbows/wrists/hips/knees/ankles + nose are placed at their MediaPipe index; **heel/toe don't exist in COCO** and are placed on the ankle with `visibility=0` (not drawn — `draw_all_landmarks` skips low-visibility points/connections — and not used in the measurements). Unused 33-slots keep visibility 0. This means `get_landmarks`, the smoothing, and the drawing work unchanged on the YOLO output. With RTMPose refinement, heel/toe get real positions + visibility (Halpe26, `HALPE_TO_MP`); the first 17 Halpe indices are identical to COCO, so `TORSO_COCO` and the color machinery work on both.
- `POSE_CONNECTIONS` now lives **hardcoded** in `skate_analysis.py` (previously pulled from `mp_vision`) and the mediapipe import is **lazy** (local, inside `analyze_frames`), so `skate_analysis.py` is importable in the YOLO venv without mediapipe.

### `skate_perspective.py` — perspective correction via track lines (phase 7)

Without correction, the push angle is measured in the **image plane**; if the camera isn't perpendicular to the plane of motion, perspective distorts the angle, and that distortion changes with the skater's position in frame. The correction calibrates the camera from traced track lines (fixed camera, one calibration per video) and recomputes the angle per frame back to the real ice plane.

- **Calibration (`calibrate_from_lines`)**: direction-of-travel lines → vanishing point V1, cross lines → V2; V1–V2 = the ice plane's vanishing line (the true horizon); f from orthogonal vanishing points (principal point at the center, square pixels); homography + camera position with the line spacing (default 4.0 m) as scale. **Condition gate on f** (`_vp_distance`, `VP_CONDITION_WARN`/`VP_CONDITION_MAX`): if the farthest vanishing point lies above 30x the image size, self-calibration of f is **refused** with an instruction to supply `f_px`; above 5x, a warning. Needed because `f² = −(V1−pp)·(V2−pp)` is dominated by that one, poorly determined point when the vanishing point is far away: on real track footage where the camera looks *along* the track, V2 sat at 133x the image size, f came out at 3.3x the image width (≈17° field of view, impossible), and **a 5 px shift on one line endpoint moved f from 3827 px to "impossible"**. Calibrated against the self-test cameras (1.0 / 1.5 / 9.3x — those all yield the correct f). **Minimal configurations**: 2 track + 2 cross lines, or 3 track + 1 cross line (cross-ratio vanishing line), or 2 track + 1 cross line + a given `f_px` — with 2+1 and no f the system is 1 DOF short, and with a (near-)**frontal camera** V2 lies at infinity and self-calibrating f is fundamentally impossible (→ `f_px` required; the error messages explain this).
- **Reconstruction (`reconstruct_angle`)**: the ankle via the line of sight onto the plane `ankle_height` (0.10 m — malleolus + skate) above the ice; the knee's line of sight is pinned down with one of two assumptions behind a single interface: `method='lower_leg'` (a sphere with radius = lower-leg length; two intersection points → a tie-break rule on direction of travel/least correction, still an open research question) or `'leg_plane'` (a vertical plane in the direction of travel). Lower-leg length is preferably measured, or `lower_leg_from_body_height()` (0.246x, Winter); `calibrate_lower_leg_length()` systematically underestimates it (dorsiflexion) and is only a sanity check. **Quality flags**: `condition_deg` (leg nearly along the line of sight) and `plane_condition_deg` (line of sight nearly inside the leg plane — precisely with a frontal camera + a direction-of-travel plane).
- **Pipeline coupling (opt-in, both backends)**: `PerspectiveConfig` (in `skate_analysis.py`) is passed through `analyze(..., perspectief=...)` → `set_horizon` (tilt from the calibration; auto-horizon is dropped) and `process_derivatives` → `_perspective_angle` replaces `calculate_angle_to_ice` at the same spot. The reconstruction works on **float pixels from `r.lm`** (`_lm_px`), not the int-truncated `lm_data` — at a distance, the lower leg is only tens of pixels. `_world_trajectory` pins the **stance-leg** ankle to the ice (the swing leg hangs higher → would distort speed) → `r.world_xy`, `r.speed`, direction of travel (with the track-line direction as a fallback). New fields: `FrameResult.angle_correction/angle_reliable/world_xy/speed`, `PushEvent.correction/reliable/speed/stroke_length` (filled in `segment_pushes`); the HUD shows correction/speed/an unreliable warning. Without `perspectief`, behavior is byte-for-byte as before.
- **GUI**: checkbox "Perspective correction via track lines (experimental)" in the `NewAnalysisDialog` **and** in the `BatchAnalysisDialog` → `CalibrationPicker` dialog (replaces the horizon step): trace lines with two clicks each (track-line/cross-line radio buttons), live calibration feedback + a drawn true horizon, fields for line spacing, focal length (0 = automatic), method, and body/lower-leg length. The table then gets Corr./v/Stroke columns; rows with an unreliable angle turn blue.
- **"Angles only" is the default** (`chk_alleen_hoeken` → `schaal_bekend=False`). **The push angle is scale-free**: it follows from the *directions* of the lines, not from their distance. Verified on the synthetic camera with 2 track lines + 2 cross lines and `leg_plane`: **0.00° error whether you enter 0.5 m, 4 m, or 50 m**. So nothing needs to be measured out to get correct angles; meters are only needed for speed/stroke length. `_scale_changed` ties that to the rest of the dialog:
  - **Method gets pinned to `leg_plane`** as long as angles-only is on, since `lower_leg` intersects with a sphere of a length in **real meters** — with a made-up line spacing that gave **49° error, silently**. That combination can no longer occur. Turning it off and filling in the real distance makes `lower_leg` selectable again (needed for an A/B of both methods).
  - The line-spacing and length fields get disabled when they don't do anything; the status line omits the camera height without a scale (it would then be in arbitrary units) and reports that speed/stroke length will stay empty. `_confirm` sets `lower_leg_l=None` for `leg_plane`, so storage and the Info dialog don't show a length that has no effect.
  - **Pitfall in `__init__`:** `_scale_changed` moves the method combo, and that signal flows through to `_recalibrate`, which needs `lbl_status`, `btn_ok`, and `_orig_w`. The initial call is therefore placed **right at the very end** of the constructor, and `_prefill` sets the scale flag **before** method/length (otherwise the coupling overwrites the taken-over choice).
- **Watch out with 3+ track lines: their spacing matters too, even with `leg_plane`.** With three or more track lines, `calibrate_from_lines` builds the vanishing line with the **cross-ratio**, and the dialog only offers one distance field — so the assumption is that they're **evenly spaced**. On a real track that's rarely the case (the blue track line, the ice/snow edge, and the boarding base don't sit at equal distances). Verified: unevenly spaced but told it's even gets **refused** ("vanishing points not consistent with a camera, f² ≤ 0") and so never silently goes wrong; with the right `rij_offsets` the error is 0.00° again. `rij_offsets` exists in the module but is **not** in the GUI — that's why `_line_hint()` adds to the error message, for 3+ track lines, that you're better off using exactly **2 track lines + 2 cross lines**, since then V2 comes from the cross lines and the spacing no longer matters.
- **The calibration is saved and reusable.** What gets saved is the **input** (`skate_perspective.CalibrationInput`: the traced lines + line spacing/`f_px`/offsets/note + the image size), not the outcome: `PerspectiveCalibration` consists almost entirely of derived matrices (R, t, C, H, H_inv) that follow exactly from that input. So it's JSON-able in `analyse.instellingen_json` (~670 bytes, no schema bump), readable by a human, and an old analysis automatically gets the benefit of a later improvement in the calibration math — the same reasoning as the events cache, which is also freshly recomputed on open. `PerspectiveConfig.to_dict()/from_dict()` do the round trip (byte-identical recomputation, guarded by `skate_perspective`'s own self-test); a config **without** `calibration_input` explicitly refuses `to_dict()`, so a correction never silently evaporates.
  - **Reopening restores the correction**: `_load_analysis_data` rebuilds the config and passes it to `process_derivatives`. If that fails, opening proceeds without the correction with a warning; an analysis from before this feature gets the old "without perspective correction" message.
  - **Reuse** (`_choose_perspectief`, shared by the single and batch flows): `skate_db.list_calibrations(bieb, beeld_w, beeld_h)` looks up earlier calibrations with the same **image size**; the user can take one over, after which `CalibrationPicker` opens **prefilled** — checking and correcting stays one action that way. `CalibrationInput.fits(w, h)` guards the image size, since the lines are in pixels: at a different resolution or crop they sit in the wrong place and the calibration yields a plausible but wrong camera pose.
  - **In a batch, the calibration is asked once and applied to every clip.** That's not convenience but a geometric requirement: a calibration belongs to one camera pose, and analyses you want to compare against each other must rest on the same calibration — tracing the same lines by hand seven times gives seven slightly different calibrations, and then you're measuring that spread instead of the effect of the correction. Clips with a different image size are skipped with a message.
  - **The Info dialog shows the calibration** (`_calibration_rows`): number of lines, line spacing, image size, method/lower-leg length, note, plus the **recomputed** camera pose (f, height, horizon, residual) — recomputed, not read from storage, so you see what the analysis would use *right now*.
  - **Pitfall:** every place that calls `process_derivatives` again must pass `perspectief=`, otherwise the angles silently fall back to the image plane. There are three of those in the GUI: `_load_analysis_data`, `_recompute` (every skeleton edit and "Determine corner"), and `_restore_original`. Before the calibration was saved, `self.perspectief` on a reopened analysis was always `None` and this went unnoticed.

### `skate_db.py` — the library (phase 1)

One library folder: `schaats.db` + `media/<analysis-uuid>/` (video copy under its original name + `landmarks.npz`) + `opnames/` (phase 8). The path lives in `%APPDATA%\SkateAnalysis\config.json` (per user, `load_config`/`save_config`, written atomically; default `Documents\SkateAnalysis`; env var `SKATEANALYSIS_LIBRARY` overrides it for tests). Config also carries `trainer_naam` (phase 4, helper `trainer_name()`). This team puts the folder in a **Google Drive** folder (Mirror mode → all files local) to share it across multiple trainers — see phase 4 below.

- **Cloud-folder discipline** (deliberate from day one): `journal_mode=DELETE` (no WAL — sidecar files sync only half the time), connections opened/closed per call (context manager `_connect`; the DB is essentially always "at rest" for the syncer, and sqlite3 objects thus also never cross a thread — saving runs in the GUI worker thread), `busy_timeout=5000`, every path in the DB **relative** with forward slashes (`_abs_path` joins it back).
- **Schema** (`open_db` creates or migrates it; `PRAGMA user_version`, now **6**): `skater(id, name, birth_year, notes, created_at)`; `source_video(id, file UNIQUE, name, bytes, fps, total_frames, status, note, updated_by, interlaced, added_at)`; `analysis(id TEXT PK = uuid = folder name, skater_id ON DELETE CASCADE, title, date, video_file, w/h/fps/total_frames, backend 'yolo'|'mediapipe', settings_json, created_by, edited, video_bytes, source_id/source_start_frame/source_end_frame, created_at)`; `push_event_cache(analysis_id, idx, leg, start_frame/end_frame, angle, min/max_angle, note)` — purely for fast list display, recomputed fresh from the landmarks whenever an analysis is opened; `source_marking(id, source_id ON DELETE CASCADE, frame, label, created_by, created_at)` — the points from the manual viewing window (v4). **Migration** (`_migrate`, step by step and cloud-safe — `ALTER TABLE ADD COLUMN` + `CREATE TABLE IF NOT EXISTS` keep it to a single file): v1→v2 adds `analyse.video_bytes` (old rows NULL → the sync size check is skipped), v2→v3 the `bronvideo` table + the three `bron_*` columns (old analyses keep `source_id` NULL, which is also correct: those came from a loose clip), v3→v4 the `bron_markering` table (old libraries simply get an empty table — there's nothing to guess), v4→v5 `bronvideo.interlaced` (NULL = not yet determined), v5→v6 the **full English rename** of every table and column (`schaatser`→`skater`, `bronvideo`→`source_video`, `bron_markering`→`source_marking`, `analyse`→`analysis`, `afzet_event_cache`→`push_event_cache`, plus every column and the `status` enum values), rewriting the whole event cache through the real pipeline (with a text-remap fallback if an analysis's npz isn't reachable) and renaming the settings-json keys covered below (phase 8, session 13). The v4→v5 step is **conditional** (`_has_column`) and that's not sloppiness: `_table_ddl` always returns the *newest* definition, so a library that only gets `bronvideo` in the v2→v3 step already has the column and would trip over a duplicate column name — exactly the path the self-test walks. Setting it goes through **`set_source_interlaced`**, not through `edit_source_video`: this is a measured property of the file, not a trainer's choice, so `updated_by` shouldn't change because of it. `_table_ddl(name)` cuts the `CREATE TABLE <name>` out of `_SCHEMA` so a fresh creation and a migration are guaranteed to use the same definition; the `REFERENCES` clause may come along in `ADD COLUMN` because the default is NULL. Two tables' historical (Dutch) DDL is frozen as `_OLD_BRONVIDEO_DDL`/`_OLD_BRON_MARKERING_DDL` so the v2→v3/v3→v4 steps keep working on a library migrating from that far back, after `_SCHEMA` stopped containing a table literally called `bronvideo`.
- **`save_analysis`**: media folder + video copy (`shutil.copy2`) + npz **first**, the DB insert (analysis + events cache in one transaction) **last**; on any error the media folder is cleaned up — so a half-written analysis never ends up in the library. Saves `aangemaakt_door` (trainer name, phase 4) and `video_bytes` (size of the copied video, for the sync check). `settings_json` carries what the npz doesn't: `smooth_n`, `threshold`, `smooth_landmarks`, `skip_corner`, `doel_punt`, `doel_kader` (the drawn box, normalized xyxy or None — turns on the spyglass in the YOLO backend and is thus measurement-relevant), `horizon_deg`, `auto_horizon`, `heavy`, `backend_name`, `perspective_used`, `app_version`, `app_commit`. `save_analysis` sets the last three **itself** with `setdefault` (so every save route — a single analysis, a batch, the self-test — sets them without having to think about it; a caller that fills them in wins). The app version comes from **`app_version()`**: reads the git repo next to the script (`git log -1 --abbrev=8 --format=%h%x09%cs` + `git status --porcelain -uno` for the "dirty" flag) → `{commit, date, dirty, label}` with `label` = `"2026-08-05 · 7e013fb7"` (a `+` = uncommitted changes), cached once per process and empty everywhere outside a git repo. Deliberately from git and not a hand-maintained constant — that drifts behind during fast development and then lies; untracked files don't count as "dirty" (videos/npz's say nothing about the logic that ran).
- **`load_analysis`** → `{'meta' (incl. parsed settings, `aangemaakt_door`, `video_bytes`), 'info', 'resultaten', 'video_pad'}`; the derivatives are empty — `process_derivatives()` + `segment_pushes()` then run afterward (the phase 0 seam). Further: `list_skaters`/`list_analyses` (with aggregates + `aangemaakt_door` from the cache; the average angle skips **incomplete** pushes — the reason text from `PushEvent.incomplete` travels along in the cache's `note` text (`INCOMPLETE_MARKERS`, one `NOT LIKE` per reason), deliberately without its own column: the cache gets recomputed fresh on open anyway, and a schema bump costs a migration. The reason texts are `skate_analysis`'s own, so caches from before the second reason keep working — `INCOMPLETE_TRUNCATED` is still literally `"truncated"`), `create_/edit_/delete_skater` (cascading, incl. media folders), `rename_/delete_analysis`, `analysis_video_path`. **`analysis_meta`** only returns the DB row + parsed settings (no npz) — that's what the Info dialog needs; `load_analysis` and `list_analyses` share the parse via `_meta_from_row`, so the list view carries the settings (and thus the app-version tooltip) without an extra query.
- **Recordings = the work list (phase 8)**: the design rule is **the folder is the truth about which files exist, the database about what we know of them**. `sync_source_dir(bieb, meta_lezer=None)` scans `opnames/`, adds new files with `INSERT OR IGNORE` (two trainers seeing the same recording at the same time don't collide) and **only writes if there's genuinely something new** — otherwise every app start by every trainer would touch the shared DB, while it's supposed to sit at rest per the phase 4 discipline. Rows for files that have disappeared stay in place (with their analyses) and are shown as "file not found"; a renamed file counts as new. **Identity is the relative path** (`opnames/<name>`), not the size: a recording that's still arriving for a colleague is, at that moment, *smaller* than what's in the DB, and with `bytes` in the key the scan would treat a half-downloaded file as a new recording. So `bytes` only does the sync check, via the existing `video_sync_status`. Further: `list_source_videos` (rows + absolute path + sync status + `aantal_fragmenten`/`aantal_schaatsers` from `analysis.source_id`), `source_video`, `edit_source_video` (status/note + `bijgewerkt_door`) and `source_fragments(bieb, bron_id)` → the stretches already analyzed, which is what gives the gray blocks in the trim window (one query instead of scanning every `settings_json` field). Statuses live in `SOURCE_STATUSES`; nothing is ever set to "done" **automatically** — the program can't know whether the trainer considers a recording finished.
- **A loose video from this PC** (`loose_video(bieb, lokaal, pad)` → `source_video_for_path`, for "View new video" in the GUI) also gets a `source_video` row, because the **points** the trainer sets hang off `source_marking.source_id` for such a row — but in the **local library** (`local_library()`: `%LOCALAPPDATA%\SkateAnalysis\local\`, env override `SKATEANALYSIS_LOCAL`), not the shared one. That's a **second library with the same schema**, not a second storage route: every function in this module works on it unchanged by passing a different `bieb` path, so the viewing window just gets `source["library"]`. Reason (11 Sep 2026): the path is local to this PC and doesn't belong on the Drive — a colleague saw nothing but a "file not found" row from it, and the user didn't want either behavior. Whatever's still in the shared DB with an absolute path from before that date gets moved by **`migrate_loose_videos(bieb, lokaal)`** (called on every refresh of the recordings list) with its points to the local library — only the rows whose file lives on this PC, since that's the PC that registered them; a colleague's row stays put (deleting it would cost *them* their points) until they themselves refresh, and `list_source_videos` doesn't show it in the meantime (default `extern=False` = the work list; `True` = loose only, `None` = everything; every row carries `library` and `extern`). Analyses trimmed from such a migrated row lose their `source_id` (ON DELETE SET NULL). Two deviations from a recording, each with a reason: (1) **`file` is the absolute path** (forward slashes, `abspath`) instead of `opnames/<name>`, and that's exactly the trait `_is_external` uses to tell the two kinds apart — no extra column, no migration, and picking the same video again finds its own points via the UNIQUE on `file`; (2) **`bytes` stays NULL**, since that size only serves to recognize a half-downloaded cloud copy — on a file that simply lives on this PC that comparison is meaningless and would work backward (the same video later re-encoded smaller = "still downloading" = the window won't open). `_abs_path` has an absolute-path branch for this: `os.path.join(bieb, "C:/movie.mp4")` would otherwise turn it into the drive-relative `C:movie.mp4`. One exception has to be handled: if the user browses to the shared library's recordings folder anyway in the file picker (`_in_recordings_dir`), `loose_video` picks the **shared** DB and the **relative** key and gets the row the scan already made for it — two rows for one file would split that recording's points in two.
- **From the camera to `opnames/`** (`copy_plan` + `copy_to_recordings`, 12 Sep 2026): the copy step that used to require Explorer. `copy_plan(bieb, paden)` decides **in advance** what goes and what doesn't (`reden`: not found, not a video, already in `opnames/`, chosen twice, already in the library, a namesake with a different size), since a thread runs during the copy that can't ask anything. **Nothing ever gets overwritten**: a recording's identity is `opnames/<name>`, and that's where the team's fragments, status, and points hang off — a different file under the same name would silently point that work at a different recording; the same size is almost certainly the same recording. `copy_to_recordings(bieb, plan, progress_callback, stop_check)` copies **block by block** (`COPY_BLOCK` 4 MB — `shutil.copy2` gives no progress and a 4 GB recording takes minutes) to a **temporary name** `<name>.part` (no video extension, so `sync_source_dir` doesn't see it — not even at a colleague's, where Drive is still pulling the half file in) and only does `os.replace` after the last byte; aborting (`CopyAborted`) or an error cleans up the partial file, one failed file gets its error as `reden` and the rest continues. `copystat` afterward keeps the recording date from the camera. In the self-test: plan reasons, aborting after the first block (no file, no `.part`, the scan finds nothing), a byte-identical full copy that the scan does pick up.
- **Points in a recording** (`list_markings` / `add_marking` / `edit_marking` / `delete_marking`, plus `aantal_punten` in `list_source_videos`): loose frame numbers with a little name the trainer sets in the viewing window. They belong to the **recording**, not to an analysis — nothing is measured, only remembered where you were — so a dedicated table with `ON DELETE CASCADE` on `source_video` instead of a column or a JSON field: there are several per recording and they need to be deletable and renamable independently. Like status and note, they live in the shared database, so a colleague sees them too.
- **Sharing (phase 4)**: `detect_conflict_copies(bieb)` reports `schaats*.db` files next to `schaats.db` itself (a conflict copy a syncer leaves behind on a near-simultaneous write; provider-agnostic, detection instead of prevention). `video_sync_status(video_pad, verwacht_bytes)` → `'missing'` / `'incomplete'` (smaller than `video_bytes` → the cloud is still downloading) / `None`, so the GUI can recognize a half download instead of crashing. **`file_is_local(pad)`** answers the other cloud question — is the file actually there, or is it fetched piece by piece from the internet? — with a **speed probe**: three 64 KB blocks at random spots, each above `LOCAL_THRESHOLD_MS` (100 ms) counts as "not local" → `'local'`/`'partial'`/`'cloud'`/`None`. Measuring instead of asking, since Google Drive for desktop sets **no** cloud attribute: its drive reports itself as an ordinary fixed disk, and a not-yet-downloaded 4 GB recording has attribute `Normal`. What *is* visible is the timing — measured 24 Aug 2026: local 0.3–2 ms per block, from the streaming folder 614 ms. **Random** spots because a block that's been read once sits in the cloud cache afterward: probing the same spot every time would say 'local' the second time regardless.
- **Self-test** (`python skate_db.py`): a round trip in a temp folder with synthetic results + a dummy video, including v1→v3 *and* v2→v3 migration (the v1 schema sits literally in there as a frozen fixture — filtering it out of `_SCHEMA` got more fragile with every bump), the recordings round trip (scanning is idempotent and ignores non-videos, status/note/`bijgewerkt_door`, `source_fragments` + fragment count, sync status of a half-downloaded recording), conflict-copy detection, `aangemaakt_door`/`video_bytes` round trip + `video_sync_status`, the shape of `app_version()` (not the content — outside a git repo it's empty) + the automatic `app_version`/`app_commit`/`backend_name` in the saved settings, `analysis_meta`, fault injection (a broken video path → no DB row, no media folder), and cascade checks.

### `skate_gui.py` — PySide6 GUI

- **Startup: something on screen first, then the heavy lifting.** Measured on a warm machine, startup took 4.2 s, and on a cold one (Defender scanning torch's DLLs + a Drive folder not yet cached) up to ~18 s, during which the screen stayed blank and the app looked dead. Two measures, in this order — with one unrelated line that still has to come before both: **`skate_environment.start_log()`** (EXE.md step 2). Bundled, there's no console (`sys.stdout`/`stderr` are `None`), and then everything that touches that stream breaks — ultralytics'/rtmlib's tqdm bar, every `sys.stdout.write`, the logging handler ultralytics hooks up on import — so that has to be settled before the first of those imports, and thus before the splash screen too (which already puts up a window at module level). The call sits behind the same `__name__ == "__main__"` line, costs ~1 ms (stdlib-only), and does nothing in the repo environment unless `SKATEANALYSIS_LOG` is set — the test hook for exercising this route without an exe. The log (`%LOCALAPPDATA%\SkateAnalysis\skateanalysis.log`, line-buffered, rotating at 1 MB) is immediately the answer to "it doesn't work for me"; the blocking backend message therefore names the path.
  1. **`SplashScreen` (QSplashScreen) before every other import.** At the top of `skate_gui.py`, the Qt import comes first (~0.1 s), then `_start_splash_screen()`, which creates the `QApplication` and shows the little window; only *after* that come cv2/numpy/QtCharts/`skate_*`. That's a module-level side effect, but deliberate: it's gated behind `if __name__ == "__main__"`, so `import skate_gui` (self-tests, measurement scripts) does nothing. The screen is drawn in code — loading an image would again be disk access at exactly the wrong moment — and `MainWindow(melding=...)` sets the phase on it ("Building window…", "Opening library…", "Scanning recordings…"); `melding()` itself does `processEvents`, since no event loop is running yet during construction. `main()` swaps the screen out with `finish(venster)` and sets `_melding` to a no-op afterward. **Pitfall:** `QSplashScreen` stays on top by default, so a modal message from startup (library unreachable, a conflict copy) would end up behind it — hence `setWindowFlag(Qt.WindowStaysOnTopHint, False)`.
  2. **Load the backend lazily.** `import skate_yolo` pulls in torch+ultralytics: 2.8 s warm and a multiple of that cold — two-thirds of the startup time, while the home page only shows the library at that point. All the GUI needs at that moment is *which* backend there is (`IS_YOLO` for two checkbox visibilities, `BACKEND_NAME` for the status bar), and `_backend_beschikbaar()` answers that with `find_spec` in ~1 ms without importing anything. The real import sits in `_load_backend()` (lock + once only), which `analyze_backend(...)` — now a function, same name and call as before — goes through, and `main()` starts `_warm_backend_up()` right after `venster.show()`: a daemon thread that does the import ahead of time while the user browses the library. `BACKEND_NAME` is a **prediction** of `skate_yolo.BACKEND_NAME` until that moment and gets replaced by the real one once loaded (so the name saved with an analysis always comes from the backend itself). If the package turns out to be installed but unloadable, the app falls back to MediaPipe and keeps the reason in `BACKEND_ERROR`, which `_warn_backend_fallback()` reports once at the next (batch) analysis — a different detector is a different measurement and may never happen silently.
  - **Measured** (warm): splash screen on screen after ~1.3 s (of which ~1.0 s is creating the first native window, which used to block the main window), main window after 2.5 s instead of 4.5 s, backend warm in the background after ~5 s. **No change in measurement**: the same clip ("Schaats frontaal.MOV", no target click) via the new route (import in the warmup thread, analysis in a worker thread) and via the old one (everything on the main thread) gives the same coverage 103/103 and the same six pushes with the same frame boundaries and angles (42.2 / 42.5 / 42.9 / 40.0 / 45.6 / 50.0°).
  - What **doesn't** come off: the ~0.9 s window construction (three pages, warm) and the cold Qt costs. Building the compare page lazily would save ~0.2 s warm there, but touches many places (`_pause_all`, `closeEvent`, `_close_compare_for`) — not done.
- **Home page = library**: on the left `list_skaters` (QListWidget), on the right `table_analyses` (date/title/duration + a buttons column, from the events cache — no npz needed, so it's fast right away; the title tooltip shows "Created by …" and "App version: …", so you can tell without opening whether an analysis still ran on old code). Double-click or "Open" → `_open_analysis_from_library()` → **`_load_analysis_data()`**: `load_analysis` → a `video_sync_status` check (missing/incomplete → a clean message that the cloud folder is still syncing) → `process_derivatives` with the **saved** `smooth_n`/`threshold` from `settings_json` → `refresh_events_cache` (so the list view stays in sync with what's in the table, even for analyses from before an algorithm improvement; if the write fails, opening proceeds anyway) → `_show_results`. The helper deliberately touches **no** `MainWindow` state (`smooth_n`/`threshold` come back as return values instead of being set on `self`), so the compare page can load analyses without overwriting the settings of the currently open analysis — which `_after_edit` recomputes from. Rename/delete with confirmation; if the **open** analysis (or its skater) is deleted, `_close_view()` and `_close_compare_for()` run first — Windows refuses to delete a still-open video, and `delete_analysis`/`delete_skater` use `shutil.rmtree(..., ignore_errors=True)`, so such a lock fails **silently**: the DB row disappears and the media folder stays behind. "Library folder..." picks the library path (`_set_library`; if the path fails, it falls back to the default folder).
  - **Duration column** (`_duration_text`): `"5.4s (4 pushes)"`, above a minute `"1:23 (12 pushes)"` — nobody reads "83.2s" as a minute and a half. `list_analyses` supplies `total_frames`+`fps` for that (already in the phase 1 schema, no schema bump). **The average-angle column is gone** (a ROADMAP extra); `AVG(angle)` stays in `list_analyses` for phase 2 and for `AnalysisPicker`.
  - **Per-analysis actions sit in the row itself** (`_make_row_buttons` → `setCellWidget` in column 3): "Open", "ℹ Info...", "Rename...", "Delete". They belong to one analysis, while the row at the bottom ("New analysis...", "Batch analysis...", "Compare skaters...") is library-wide — mixing them on one bar was confusing. Each button gets its analysis id via a **default argument in the lambda** (`lambda _=False, a=aid: ...`); without that every row would capture the last loop value, and the `_=False` swallows `clicked`'s `checked` parameter. `_rename_analysis(aid, huidig)` / `_delete_analysis(aid, titel)` got those parameters for that, with `_selected_analyse_id`/`_selected_titel` as the fallback. Column widths: only the title is `Stretch`, the rest `ResizeToContents` (four buttons don't fit in a quarter of the table width), and the **row height has to be set by hand** (`setRowHeight(rij, knoppen.sizeHint().height() + 4)`) — a `QTableWidget` doesn't automatically grow to fit a cell widget.
- **Recordings — trimming fragments (phase 8)**: the home page has two tabs (`tabs_library`) — "Skaters & analyses" (the existing splitter panel) and **"Recordings"**. Two tabs and no third column, because recordings don't belong to any one person: it's a **work list for the team** (the folder sits in the same shared Drive), so they don't hang off the skater selection on the left.
  - `_refresh_recordings` (runs when the library opens/switches and on "Refresh") does `sync_source_dir` + `list_source_videos` and fills `table_recordings`: file name, duration, **status** (a combobox in the row → `edit_source_video`), fragment count (`3 fragments · 2 skaters`), and an **inline-editable note** (only column 4 is editable; the `_filling_recordings` flag suppresses `itemChanged` while building, and the status combo is only connected *after* `setCurrentIndex` — otherwise every refresh would fill up the DB). A missing file stays in the list as "(file not found)" in gray.
  - **Column "On this PC"** (`OPNAME_KOL_*`, `LOKAAL_WEERGAVE`): is the recording available offline on this machine, or does the footage come from the cloud while viewing? Measured on a library in a Google Drive **streaming** folder (24 Aug 2026, `00005.MTS`, 4.2 GB): a single jump in the trim window pulls in ~40 MB and costs **5 to 20 s**, against **30–120 ms** if the same recording is local; with a network counter alongside it, confirmed that ~40 MB moves per jump and not everything from frame 0 (MPEG-TS has no index, so ffmpeg binary-searches for the timestamp). Nothing can be improved about that in code — `_read_frame_exact` already seeks straight to the target instead of scanning forward — so the win is in **saying so**: `_warn_not_local` (hooked in behind `_recording_available`, so before both trimming and viewing) shows the numbers plus the fix (folder 'opnames' → Google Drive → 'Available offline') and lets the user continue anyway. What *does* download everything in between is fast-forwarding at 2x/4x/8x: that does a per-frame `grab()`.
  - The probe runs on a **background thread** (`LocalProbe`, one `measured` signal per recording), since exactly the interesting case takes time: ~0.5–1.2 s for a recording that's in the cloud, milliseconds for a local one. Until there's a result, the cell shows "—", not "no". `_refresh_recordings` restarts it (a status can change while Drive is downloading) and `closeEvent` aborts it — destroying a running `QThread` is a crash.
  - **`_clip_recording`** is the whole flow: a sync check (`missing`/`incomplete` → report it and don't open, instead of letting the trim window crash on a half-downloaded recording) → confirm a skater exists at all (before the marking work, not after) → `FragmentPicker` → `_clip_to_temp` (a `QProgressDialog` around `trim_fragments`; `wasCanceled` is the `stop_check`, and progress is reported in percent so `setValue` absorbs most calls without processing events) → `_new_batch_analysis(voorgevuld=...)`. **Nothing new happens after trimming**: each fragment is a plain video file, so the existing batch flow (target/horizon choice per clip, `BatchWorker`, `save_analysis`) does the rest — no second analysis pipeline and no second save route. `BatchAnalysisDialog` got `voorgevuld` + `_voeg_rij(pad, titel, bron)` for that, which hangs the `source_*` fields off `Qt.UserRole + 1` of the first cell so they end up in `save_analysis` via `taken`. The temporary fragment folder gets cleaned up as soon as the batch finishes (or on cancel/close) — `save_analysis` already has its own copy in `media/<uuid>/` by then. **Note:** `_new_batch_analysis` now takes a parameter, so the button connects via a lambda — `clicked` would otherwise pass its `checked` bool as `voorgevuld`.
  - **Combing on an interlaced recording** (see step 0 in the analysis core): `_recording_available` finishes with **`_source_interlaced(bron)`**, which measures the recording once and stores the answer in `source_video.interlaced`. There, not in the window itself, for two reasons: both windows (trimming and viewing) go through it anyway, and on a streaming Drive that measurement costs seconds — it shouldn't fall halfway through opening. The outcome goes to `FragmentPicker(deinterlacen=…)` and `ViewWindow` (which reads it from the `bron` dict), so the viewing window shows the same clean picture a media player would give, and to `trim_fragments`, so the fragment stays permanently clean. If the measurement fails, **don't** filter — better the raw picture than touching pixels based on a failed measurement.

  - **Keeping it usable on a half-hour recording** (measured on `00005.MTS`, AVCHD 1920×1080 @ 25 fps, 34,728 frames ≈ 23 min, 4.2 GB — decoding there costs ~9 ms/frame, a `grab()` ~3 ms, and a seek ~80 ms, so **the decoder isn't the problem, how often you call it is**). Three things, each necessary:
    1. **Every step backward seeks** in `fast_seek` mode, however small. The sequential route reopens the video and scans from frame 0; one frame back at frame 20,000 used to cost ~84 s with the GUI fully frozen. Now 99 ms. Only *small* forward jumps (≤ `SEEK_THRESHOLD_FRAMES`, 30) stay sequential: those are cheaper than a seek and keep stepping frame by frame around a boundary exact.
    2. **Scrub coalescing** (`_scrub_requested`/`_scrub_tick`, only in `fast_seek` mode): dragging across the timeline fires hundreds of `valueChanged` signals at ~100 ms of work each, piling up into what looks like a hang. The slider now only puts the requested frame into `_scrub_target` and a **`QTimer` with interval 0** draws it — which only fires once the queue is empty, so all intermediate values fall away and drawing happens exactly as often as the machine can keep up with. Measured: 300 signals processed in 1 ms, one draw. If a new target arrived while drawing, `_scrub_tick` reschedules itself.
    3. **The window has to fit on a laptop screen.** At 1280×800 (working area 752 px), the trim window used to require at least 723 px; with the title bar, the button bar — and with it "Done" — fell just below the screen edge, and `resize()` can't fix that (see `set_window_size`: a window can't go below its `minimumSizeHint`). Fixed by lowering the minimums: video floor 560×300 → **400×200**, fragment table 120 → 70 px, a shorter instruction text and tighter layout margins → **553 px** minimum. `set_window_size` is deliberately called **last** in `__init__`, against a complete layout. Watch out when extending this window: `min_size` of `VideoPlayer` is the label's explicit `setMinimumSize` and thus feeds straight into the window height (a QLabel's `minimumSizeHint` with a pixmap — the pixmap's size — would lose that). Measured minimum heights of the other dialogs on this same screen: `TargetPicker` 426, `HorizonPicker` 495, `NewAnalysis` 290, `Batch` 315 — those fit. **`CalibrationPicker` fits too** (verified 11 Aug 2026: `minimumSizeHint` 1008×460, opens at 1150×700); an earlier note claiming it was 1724 px wide is wrong.
    4. **Speeds above 1x** (`SPEEDS` now has 8x/4x/2x): those don't decode faster, they **skip** frames — `_speel_stap()` shifts four frames per tick at 4x on the normal fps interval, since 4x real speed (decoding 100 fps) can't be delivered by any decoder. Without this, 1x was the ceiling and watching through once took 23 minutes. `SPEED_DEFAULT_IDX`/`ALL_SPEED_IDX` are looked up with **`_speed_idx(factor)`** instead of hardcoded numbers, otherwise every added speed silently shifts the defaults.

- **`PlayerKeys(QObject)` — one keyboard standard for *every* video.** Video plays back in four places (view page, compare page, trim window, viewing window), and those only shared the mouse: the viewing window had space/`.`/`,`/arrows, the trim window only `S` and `E` (as a `QShortcut`), and the two pages in the main window had nothing — everything there had to go through the buttons. This class *is* that handling, written once; each site keeps only its own extras (`extra={Qt.Key_…: callable}`). **The standard**: space = play/pause, `.`/`,` = scrub at 6x for as long as the key is held, ←/→ = one frame, Home/End = start/end, F11 = full screen. **The extras**: viewing window `P`/`1`–`9`/`Del` (points), trim window `S`/`E`/`Del` (fragments), analysis page Ctrl+Z/Ctrl+Y (stays a `QShortcut` — that has a modifier, see below).   - **A filter on the application**, not `keyPressEvent` or `QShortcut`: after one mouse click, focus sits on a button or the timeline, and those swallow space and the arrow keys respectively before the window sees them. Three things follow from that: the non-key branch has to be **short** (every event of the whole app passes through here — `return False` right away); a focused **text field** keeps its own keys, otherwise a point can't be renamed and `S` would start a fragment while typing in the "go to m:ss" field (exactly what the old `QShortcut("S")` did); and keys **with a modifier** pass straight through, so Ctrl+Z keeps working and Ctrl+← doesn't silently scrub back a frame.
  - **Scrubbing with `.` and `,` at 6x.** Holding scrubs, releasing stops; a short tap shifts exactly one frame, since `start_scrubbing` takes that first step immediately (both ways such a key gets used). The target frame follows from the **wall-clock time** since the key press (`_scrub_tick`, same motive as the compare page's master clock), not a fixed step per tick: that way it's genuinely 6x recording speed, even if the decoder can't keep up — backward, every step costs a seek (~80 ms against a tick of `SCRUB_TICK_MS`=40 ms), and then more frames get skipped instead of the scrubbing slowing down. **Autorepeat is skipped** (`event.isAutoRepeat()`): while held down, Windows sends a stream of press/release pairs, and those would restart the scrubbing every ~30 ms — resetting the wall clock to zero each time and stalling it completely.
  - **Which players are controllable is a callable**, since that depends on the state of the window; `active` is the condition above that (is the right page even open). The main window therefore has **two** instances instead of one with a page branch halfway through the handling: on the compare page, two players are driven at once and space controls the **master clock** (`on_play`), since two separate frame timers drift apart within seconds — resuming wherever the videos are, not from the sync point (only the "Start all" button does that). Whoever passes `on_play` must also pass **`is_playing`**: under the master clock, each player's own play timer stands still while the picture keeps running, and without that answer space would restart playback instead of pausing it.

- **Zooming in on the skater** (mouse wheel over the video + a zoom slider 1x–5x + a "Fit" button + a "Follow skater" checkbox): **crop-and-magnify at the single scaling point** `_show_pixmap` — a crop around the pan center point is scaled up to the label *after* drawing the overlay (so overlay + skeleton get magnified too and stay pixel-correct). The crop keeps **the same aspect ratio as the frame** (`cw=w/zoom, ch=h/zoom`), so the KeepAspectRatio letterbox — and with it the editor's coordinate conversion — stays unchanged. One source of truth, `_crop_norm` (set from the *integer* crop, not float, against ~1px drift), is read by the player's coordinate functions (`widget_to_norm`/`norm_to_widget`, public) and, via `self.player.crop_norm`, by `_draw_handles`; at zoom=1, `_crop_norm=(0,0,1,1)` and everything falls back byte-identically to the old behavior. This way, the phase-3 skeleton editor works pixel-correctly at any zoom level (the core goal: placing points more precisely on a skater far away). **Auto-follow** (`_zoom_follow`, checkbox): centers the crop on the torso midpoint via the shared `torso_centroid`, but only on a genuine frame change and not during a handle drag (`follow_frozen`, set by the editor — otherwise the crop would jump away from under the cursor). **Manual panning** = left-drag **outside** edit mode (inside the editor, left-drag = move a point). Those pan branches sit at the top of the player's own `_mouse_press/_move/_release`, *before* the callback to the editor — that priority order is guaranteed by construction, and turns off auto-follow. **Pitfall:** the crop is always taken from a `.copy()` of the slice — that makes it C-contiguous for the QImage stride and keeps `_last_frame` at full resolution (needed to zoom back out without re-reading); never mutate `_last_frame`. The HUD/ice line (fixed full-frame positions) can fall outside the crop when zoomed in — expected/acceptable.
- **Automatic zoom** (checkbox "Automatic zoom", `_zoom_auto`, off by default): filmed frontally, a skater grows 1.4–5.8x in frame over the course of one clip (measured across the library), so a single fixed zoom factor is only correct for a few seconds. With this on, the program determines the zoom itself from the skater: they stay **entirely in frame with `BOX_MARGIN` (15%) of air around them**, the whole clip. Hence **two zoom values**: `_zoom` = what the user set (slider/wheel, 1–`ZOOM_MAX`) and `_zoom_eff` = what `_show_pixmap` applies (up to `ZOOM_AUTO_MAX` 8x, further than the manual limit). All geometry (crop, pan clamping, the pan-vs-editor priority in `_mouse_press`) works off `_zoom_eff`; only the slider/wheel work off `_zoom`. As long as the automatic mode is on, the zoom slider and "Fit" are **disabled** (the slider still moves as a read-out) — more honest than a control that does nothing; turning the mouse wheel turns the automatic mode off and takes over the current setting (the same way manual dragging takes over from auto-follow).
  - **Box signal**: `box_sequence()` (in `skate_analysis.py`, the recipe of `determine_horizon_sequence`) computes `(center_x, center_y, radius)` once, offline per frame, when `load()` runs. The center is the **midpoint of all visible landmarks**, not `torso_centroid` — that sits high on the body, so a box around it gives as much air above the head as below the skates (measured: frame fill 0.40 → 0.56). The radius is the distance from that center to the farthest point, so to an extended leg. Gaps and outliers (Hampel) removed; the center gets a short smooth (`BOX_CENTER_S`, 0.5 s), the radius first gets a **running maximum** over `BOX_SMOOTH_S` (1.5 s ≈ one stroke) and *then* Savitzky–Golay: smoothing alone would flatten the peak and an extended leg would fall out of frame, while the maximum is an envelope that covers that moment's widest stance yet moves slowly (<2% zoom change per frame, so no pumping). `BOX_POLY=1` instead of the shared `SMOOTH_POLY=2`: the quadratic edge fit extrapolates the stroke wave and is off by 15% on the first frame (linear: 3%). Computing it ahead of time instead of online makes the crop independent of playback direction (scrubbing = playing). No usable pose in the whole analysis → `None` → everything behaves like a fixed zoom.
  - **Detection gaps**: a gap up to `BOX_GAP_S` (1 s) gets bridged with the last known box; longer than that, the box smoothly opens up to the full frame — otherwise you'd be staring at an 8x magnification of where the skater *used to be* (that literally happened, see the leading gaps in IMG_9002). The blending happens in zoom space (`0.5/radius`), not in the radius itself: up close the radius is small, and there a linear blend would collapse the zoom within a few frames (measured 14% → 3% change per frame).
  - **Following**: with automatic mode on, the crop follows the box midpoint (which the zoom is also measured against, so the skater is guaranteed to fit), manually the more calmly moving `torso_centroid`. A deliberate zoom action may recenter immediately (`_force_follow`), while an editor drag or a layer toggle must not.
  - **Ceiling** (`_zoom_ceiling`): not the video resolution but the **on-screen magnification** counts — `BOX_MAX_MAGNIFICATION` (2.5) screen pixels per video pixel. A portrait phone clip already sits heavily shrunk in a landscape panel and may thus zoom in far; 4K landscape barely at all. The user chooses nothing here, so the program shouldn't hand over mush.
- **Drawing on the picture** (mouse combo ✋ Pan / ✏ Sketch / 📏 Line + ↶ and 🧹 in the same bar, `VideoPlayer._draw_*`): a trainer's annotations over the picture — a free sketch or a straight line from press to release, in magenta at `DRAW_OPACITY` (70%) so the picture underneath stays visible. Lives in `VideoPlayer` but is only **on** in the viewing window (`show_drawing=True` from `ViewWindow`): that's the window where you *watch* and point things out, while the left mouse button is already taken on the view and compare pages (panning, skeleton editor) and in the trim window you're setting boundaries, not discussing technique.   - **A drawing belongs to the clip, not to a frame.** It lives in `self._drawing` on the player, not in `FrameResult`, so it stays put while the video plays on or you scrub — that's the point: you mark a line and then play on to see whether the skater crosses it. That way the drawing sticks to the picture: zoom in or pan, and it moves along (verified: at 2x zoom, the middle of the line stays at the same picture position and it's twice as long on screen). In widget coordinates it would sit next to the skater after the first zoom step. A drag into the black letterbox gets **clamped** to the picture edge instead of rejected, and a drag shorter than `DRAW_MIN_DRAG` counts as a click (otherwise every stray click leaves a dot behind).

Right-drag always pans, even mid-drawing, so panning stays reachable without switching modes. The skeleton editor wins from drawing: `edit_mode` is therefore a **property**, whose setter resets the mouse to pan and locks the combo — a drawing mode that silently does nothing (or worse: swallows a drag that was meant to move a landmark) is the worst of the two outcomes. The drawing itself just stays where it was. In the viewing window there's no skeleton editor, so in practice the two never meet — it's the safety net for if the flag ever gets turned on somewhere else.

- **Skeleton editor (phase 3)** — the "Edit" button (`_toggle_editing`, `editor_bar`) on the view page: playback pauses, every visible landmark of the current frame gets a draggable handle (`_draw_handles`; grab/draw radius `_handle_radius` = a fraction of the on-screen torso length, clamped to `HANDLE_MIN_PX`/`HANDLE_MAX_PX` — so the dots look the same size for any skater size or zoom level). Dragging (the editor's mouse handlers) moves the point (`_set_landmark`; `Landmark` is immutable → replaced), hovering shows the body part under the cursor (`_show_hover_name`, `LANDMARK_NAMES`). On release, the move tapers out to ± N neighboring frames (`spin_uitvloei` → `_taper_frames`) with a cosine falloff `0.5·(1+cos(π·k/N))`, stopping at a detection gap; the dragged point gets `visibility=1.0`. Works on the **smoothed** landmarks (what you see is what you edit) — smoothing does **not** rerun after an edit. After every drop: `_recompute` → `process_derivatives` + `segment_pushes` (no smoothing) → table/chart/HUD update live, plus **auto-save** via `skate_db.save_edited_landmarks` (overwrites `landmarks.npz`, creates `landmarks_ruw.npz` as a pristine backup on the *first* edit, sets `analysis.edited=1`, refreshes the events cache). Undo/redo (`_undo_edit`/`_redo_edit` stacks; per edit: landmark index + old/new per frame). "Restore original" (`_restore_original` → `restore_original_landmarks` → `refresh_events_cache`) restores `landmarks_ruw.npz` and `edited=0`. Only **editable** where the pose sits in memory as a list of mutable `Landmark` tuples (`_frame_editable`) — so not in the raw "no smoothing" diagnostic mode.
- **Placing a skeleton on a frame without a pose** (phase 3, second half) — a gap frame breaks the stance run in `determine_push_from_extension` and yields `INCOMPLETE_TRUNCATED`, so two missing frames can cost a whole push measurement; that's fixable by closing the gap by hand. In edit mode, **"➕ Create skeleton"** (`_start_placing`) is active on such a frame, with **two routes** — and the first is by far the usual one:
  - **Take over + drag (default).** If the neighboring frames provide a usable prefill (every point in `PLACEMENT_REQUIRED` visible), that skeleton gets placed right away, recorded as one `'skelet'` undo item, and saved, and the frame is from then on a **perfectly ordinary editable frame**: correcting it works with the existing drag editor. One way of working for *every* frame, and more intuitive than reading and clicking through eight names.
  - **Click sequence (only if there's nothing to take over).** If there's no pose anywhere else in the analysis, there's nothing to drag from either. Then `place_bar` asks for the points one at a time in `PLACEMENT_ORDER` (shoulders, hips, knees, ankles — exactly what the measurements use plus the torso that `_handle_radius` and auto-zoom rely on; heel/toe stay at visibility 0 just like the YOLO backend without RTMPose), with the requested point shown as an orange ring-with-crosshair in `_draw_handles`. The `place` branch sits **first** in the editor's mouse press/release handling and always swallows the click: the frame *is* editable during the sequence, so without that priority a click on an already-placed point would start a *drag*. Clicks outside the frame are rejected rather than clamped (clamping would silently put the knee on the picture edge).
  - **Prefill** (`make_prefill` in `skate_analysis.py`, next to `box_sequence`): a short gap (≤ `INTERP_MAX_S`) between two poses → linear interpolation; a longer gap → copy the nearest pose (blending over half a second melts limbs together); no pose anywhere → 33× visibility 0 at the center of the frame (and then the click sequence runs). Always exactly 33 landmarks, since `results_to_arrays` indexes blindly into a `(n, 33, 3)` array.
  - **`r.pose_found = True` gets set right away**, followed by recomputation: without filled-in `lm_data`/`been`/`hoek`, the very next redraw breaks (`draw_leg_overlay` indexes `lm_data['l_hip']`, `_update_live_status` does `been.upper()`). That's why `_after_edit` is split into **`_recompute`** (recompute + display) and **`_save`** (`save_edited_landmarks`): the take-over route does `_after_edit` (both), but during a click sequence nothing may go to the library yet, since that sets `analysis.edited = 1` and creates the pristine backup — irreversible if the user cancels.
  - **Recording a click sequence** can only happen once every point in `PLACEMENT_REQUIRED` (hip/knee/ankle L+R) has a visible position; otherwise a frame with those three points on top of each other would enter the table as a push angle of 0°. `_stop_placing` is the fail-safe exit on every interrupting path (scrubbing away via `_player_frame_shown`, leaving edit mode, switching pages, opening another analysis, `closeEvent`): kept if something was clicked and the skeleton is complete, otherwise rolled back — accidentally scrubbing away must not lock in a prefill as a measurement. When committing, `self._plaats` is released **first**, since `_after_edit` redraws and comes back here via `_player_frame_shown`.
  - **Undo items are typed**: `'sleep'` (landmark index + old/new per frame) alongside `'skelet'` (frame index + the whole `lm` list + `pose_found` + the clicked set), handled by `_apply_edit`. The list is stored as a `list(...)` copy — `_set_landmark` mutates in place, so a direct reference would keep changing along with later edits.
  - **Zoom/pan stay available**: the mouse wheel zooms, and **right-drag pans** (a new branch in `VideoPlayer._mouse_press`, works regardless of `edit_mode` — the left button is taken). The label is therefore set to `Qt.PreventContextMenu`, otherwise every pan would pop open the `QMainWindow`'s toolbar menu. `follow_frozen` stays on for the whole sequence so the crop doesn't jump between two clicks, and `speler.recompute_box()` (new) runs when starting/committing: `box_sequence` opens up to the full frame past a gap > `BOX_GAP_S`, so without recomputing, the exact frame being annotated would start fully zoomed out.
  - **Counter + navigation**: `lbl_coverage` (a permanent status-bar widget next to `lbl_live`, filled by `_update_coverage` from `_recompute`/`_show_results`) shows "Skeleton: 123 of 126 frames" (with "· N in the corner" appended if there are corner frames); **"⏭ Next gap"** (`_go_to_next_gap`) jumps to the next frame without a skeleton and wraps around. What counts as a gap is decided by **`_is_gap()`**: no pose *and* no corner — closing a gap in the corner by hand is wasted work, so those frames stay out of the count, out of "Next gap", and keep "➕ Create skeleton" disabled. `_gap_position` reports alongside it which one of how many this frame is within its gap — closing half a gap doesn't change the table yet, since the stance run breaks off on *any* skeleton-less frame.
- **Adjustable playback speed** (`_set_speed` → `_play_interval_ms`): the play-timer interval scales with the chosen factor relative to the video fps, so a push can be watched slowed down.
- **Playback runs on the wall clock** (`_play_tick` + `_calibrate_play_clock`): the frame to show follows from the time elapsed since the calibration point (`basis_idx + verstreken × fps × factor`), not "previous + 1". That difference is invisible as long as one frame fits within the tick interval, and decisive the moment it doesn't: then the video plays back **slowed down and jerky** instead of skipping frames, since every outlier in decode time piles directly on top. Not an edge case — measured on this laptop (1280×800, dpr 2), a 1080i camcorder recording in the viewing window only reached **13.1 fps of the 25 (53% of real time)**, and even without the comb filter every clip got stuck at 85%, because a Qt timer of 40 ms fires around 47 ms on Windows due to clock granularity. With the wall clock, every combination measured reaches **99–100% of real time**; a shortfall gets paid in skipped frames, and that only costs a `grab()` (~3 ms) since `_read_frame_exact` scans sequentially past them anyway. **The timer has to be set to `Qt.PreciseTimer`** for this (set on `play_timer`, the master clock, and the scrub timer): a plain Qt timer is a `CoarseTimer` and on Windows hangs off the ~15.6 ms clock granularity, so a 40 ms timer measured actually fires once per **46.5 ms** — structurally 6.5 ms too late per frame, which the wall clock dutifully settles as 15% dropped frames while there was plenty of compute time left. With `PreciseTimer` it fires at 40.1 ms. **What still falls away after that is load, not shortfall**: the work is 27.9 ms per frame (reading 15.9 + showing 12.0) out of the 40 available, and the same measurement repeated three times gave 5%, 12%, and 23% dropped frames at a steady 99% real time — the spread is in whatever else the machine is doing, not in the pipeline. That last part got resolved with the `ForwardReader` below. **And the timer has to fire more often than the frame rate** (`PLAY_OVERSAMPLE`, 3x, floor `PLAY_TICK_MIN_MS`). The wall clock corrects the *pace*, but a frame can only be shown at a moment the timer fires — if it fires exactly once per frame, any tick that's a few ms late costs a *whole* frame right away. At 25 fps that doesn't show (40 ms interval, a good 20 ms of slack); at **59.22 fps** — a screen recording of a TV broadcast — the interval is 16 ms against a frame of 16.886 ms, and that 0.9 ms of slack gets eaten by ordinary Windows jitter. Measured on "kjeld in inzell" (1180×670 @ 59.22 fps, this screen at dpr 2, three 6 s runs): **92–93% of frames with 13–17 double-steps**, against **96–97% with 2** once the timer runs at a third of the frame interval; the compare page shows the same pattern (see there). The number of **double-steps** is the measure that matters here — that's what reads as stutter; the tick itself only cost ~5 ms, so it wasn't a compute shortfall but a timing-precision one, and the percentage alone wouldn't have found the bug. Oversampling further (1/4) gained nothing more, and an empty tick (target not yet reached) costs ~0.02 ms, so the 165 ticks/s at 1x are negligible. Two things were measured along the way in this same pass: the `QImage(...).copy()` before `QPixmap.fromImage` is **gone** (it used to copy the whole frame a second time while `fromImage` already copies during conversion to the platform's pixmap format — 0.6 ms of a 5.3 ms tick, and the picture shown is pixel-for-pixel unchanged), and the tempting step of scaling straight to **screen pixels** (`cv2.resize` + `setDevicePixelRatio`, so Qt has nothing left to blow up when painting) turned out to be **more expensive**: tick 5.6 → 8.4 ms and delivery dropped to 83%.
- **Reading ahead during playback** (`ForwardReader` + `_start_readahead`/`_stop_readahead`): showing a frame consists of two halves that don't need anything from each other — **reading** (decoding + comb filter, 15.9 ms on 1080i camcorder footage) and **showing** (crop + QImage + scaling to a HiDPI screen, 12.0 ms). Back to back on the GUI thread that's 27.9 ms of the 40: enough on average, too little for a spike, and every spike costs a frame right away. A `QThread` now does the reading, the GUI thread only the showing. **Measured A/B on `00005.MTS`: GUI work per tick 21.1 → 7.2 ms median (p90 23.3 → 10.4), reproducible over six rounds.** When checking these numbers, watch for the **right** measure: the **number of dropped frames** is a poor metric because it's entirely dominated by machine load — the same measurement six times gave 24/23/7% without the reader and 8/26/0% with it, so nothing can be read from that. What the reader buys is **headroom**: the GUI thread now has 7 ms of work out of the 40 instead of 21, so there's three times the margin before a spike costs a frame. That this works in Python isn't a given: it only works because OpenCV releases the GIL during `read()` and the filter steps. **Precomputing every frame isn't possible** — one 1080p frame is 6.2 MB, so `00005.MTS` would cost 216 GB and a 9.2-minute wait, and even 10 seconds of video already costs 1.6 GB; the buffer is therefore capped at `READAHEAD_MAX_BYTES` (96 MB, ~16 1080p frames and ~3 4K frames) — enough to absorb a spike of a few frames, which is the whole point. Four things belong with it:
  - **Whoever holds the capture does the reading.** A `cv2.VideoCapture` isn't thread-safe, so the player hands it off on `speel()` and gets it back on `pauzeer()`, `go_to()`, `load()`, and `sluit()` — never two readers. `go_to` is random access and therefore always stops the reader; if the video keeps playing, `_play_tick` restarts it at the new spot.
  - **The unshown frames travel back too** (`remaining()` → `_readahead_rest`, read out at the top of `_read_frame_exact`). On handoff, the capture sits up to 16 frames ahead of what's shown; without that transfer, a step **forward** after pausing would count as a jump back and reopen the video, scanning from frame 0. Measured on the view page: that step costs **5.2 ms** with the transfer, 23.6 ms without — and the picture is correct either way.
  - **Only up to and including 1x.** Above that the player skips frames and `_read_frame_exact` reads the frames in between with a bare `grab()` (~3 ms); a read-ahead reader would decode every one of them and become the bottleneck itself (8x asks for 200 fps, it delivers ~63). Verified that no reader runs at 4x.
  - **The compare page needs it the most** — two players side by side, so every bit of work counts double — but drives them from `MasterClock._tick` with `go_to`, and that's exactly the random access that stops the reader. For that there's **`show_on_clock(idx)`**: the same step, but as sequential-forward under an external clock, so it does use the reader (jumping back falls back to `go_to`, above 1x to the grab-skip). Measured with two 1080i recordings: one tick at 1x used to cost **56.4 ms** against a tick interval of 30 ms, now **12.8 ms** (p90 58.8 → 15.9); at ¼x, 14.0 → 0.0 ms. The first tick after "Start all" costs a one-time ~0.25 s warm-up (first decode + first pixmap), same as before this change. `MasterClock.stop()` also pauses the players that were running under it: their own timer already stood still, but their reader didn't — and that holds the capture plus up to 96 MB of frames nobody's waiting for any more (only those players, see the compare section: pausing everything used to make ▶ per side unusable).
  - **Frame-exactness verified** on deterministic material (`00005.MTS` — note: the Amber clip doesn't decode reproducibly on frames 1, 4, and 7 by itself, an AVCHD fragment starting mid-GOP, and so is unusable as a reference). With `fast_seek=False` — the measurement pages — no deviation at all: not during playback, not on stepping forward after a pause, and the order is strictly increasing. With `fast_seek=True`, **backward** steps are inexact, but that's the existing seek and happens just the same with the reader disabled. Same shape and motive as the compare page's master clock (`MasterClock._tick`) and the scrubbing in `PlayerKeys`. Two things belong with it: `_set_speed` has to **recalibrate** (the factor otherwise applies retroactively to the time already elapsed), and `_play_tick` recalibrates itself the moment `huidige_idx` isn't the frame it last showed itself — then something got scrubbed or jumped to in between. `_play_step()` has since only determined the tick frequency, no longer which frame comes next.
- **The table and the video are two-way traffic**: a row click seeks the video; during playback, the active push event's row is highlighted (`_mark_active_row`), with `blockSignals` to prevent a signal loop.
